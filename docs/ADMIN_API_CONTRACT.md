# Bounded Admin read contract

All routes are same-origin authenticated administrative POSTs, with existing CSRF and example-mode isolation.

- `/api/knowledge/admin/browse`: `{section,filters?,offset?:0,limit?:25,example?}`
- `/api/knowledge/admin/detail`: `{kind,id,revision?,example?}`
- `/api/knowledge/admin/history`: `{kind,id,offset?:0,limit?:25,example?}`
- `/api/knowledge/admin/graph`: `{filters?,level:"overview"|"steps"|"all",submission_id?,example?}`

Pagination integers reject booleans, offset is nonnegative, limit is 1–50. Ordered offset pages include `{offset,limit,total,has_more}`. New/changed records may move between pages; Refresh begins again. No whole-dataset client cache or accumulation is required.

Filters: `team,system,scope,query,type` (strings <=500), `state` (all/reported/proposed/awaiting_clarification/confirmed/disputed/rejected/stale/superseded/active/pending/processing/completed/failed/unknown), `freshness` (all/recent/older), `submission_id` UUID, `revision` positive integer, `latest_only` boolean. Entity/group type uses `type`; entity member selection also accepts `exclude_group_id` UUID. Empty strings mean no text filter. Text matches use Unicode NFKC normalization and case folding and literal substrings (percent/underscore are not wildcards). Revisions are matched together with their submission for system filtering.

Browse sections: `overview,submissions,connections,entities,groups,jobs`.
Response: `{section,items,page,analysis_limitations}`. Overview also includes `counts` with process, revision and open-decision totals.
- submissions: metadata includes the presentation title in `display_name`, the original `context.process_name` and `context.process_owner`, revision attribution and job status. Name search includes the presentation title. `latest` is false for a revision that a later revision of the same submission has replaced; the list shows it as superseded. `capture_incomplete` is true when the revision was filed while capture was still running, or with notes or a working map that stopped before the last answer; it is false when the capture was complete or was not recorded.
- connections: proposal metadata, endpoint IDs/revisions/names, status/review_version/relationship_type/explanation/condition/scope/stale_reason; no evidence/history.
- entities: `{id,submission_id,revision,type,label,latest,canonical_id?,process_name,step_count,step_label}`; no data. A role, system, team, scope or business object is one entity per revision however many steps name it (matched on type and case-folded label; the first spelling is the label); each mention is its own relationship with that step's evidence. `process_name` is the presentation title of the entity's process, `step_count` the number of steps that name it and `step_label` the first of them (null for a step itself). Revisions filed before this rule keep their one-entity-per-step records.
- groups: group metadata plus member_count, alias_count, history_count; no full lists.
- jobs: job metadata plus process_name and `detail`, what the job's last run did (`{}` before any run): `candidates` (processes compared, at most eight) and `candidates_omitted` (compatible processes not compared); after a completed run `proposals_returned`, `proposals_kept`, `proposals_dropped` and, when any were dropped, `dropped_reasons` (`{validator sentence: count}`); after a failed run `error_kind` (`provider`, `result` or `internal`) and `error_class`. `error` is the sentence for that kind; only a provider error carries the provider message this app worded.
- overview items empty; counts includes submissions, awaiting_review, confirmed_connections, processing_failures, processing_stalled, entities,groups,jobs,connections. `processing_stalled` counts jobs still `pending` more than five minutes after they were filed (no provider was configured, or a stop left them); `processing_failures` counts only `failed` jobs.
- `/api/knowledge/status` (the submitter's capability, not an Admin route) answers `{submission_id,revision,job_id,status,error,attempts,stalled}`. `stalled` is true when the job is `pending` and no worker of this app holds it; when a provider is configured and the job has been started fewer than three times, the call queues it first.

Detail kinds: `submission,entity,relationship,proposal,group`.
Response: `{kind,item,submissions,entities,edges:[],proposals:[]}`.
- Submission requires revision and returns its full saved account, including complete transcript. `graph_source` (`draft` or `workflow`) names the map the stored graph was built from: the review draft, or the working map when no draft existed or an unedited draft predated newer answers (`draft_stale` true, `draft_edited` not true, and the working map has steps or the draft has none). The `process` and `process_version` entities record the same `source` with `draft_stale` and `draft_edited`. `capture`, present when the submitting browser recorded it, is `{in_progress,notes_current,map_current,notes_through_turn,map_through_turn,answers,notes_answers,map_answers}`: the `*_current` flags are true, false or null (not known), the `*_through_turn` values are participant turn IDs of that revision or null, and the three counts are derived by the server. `notes_assumed` / `map_assumed` are present, and true, only when the interview was reopened from a file without a capture record and answers were added since: the turn named is then where that file stood, not a recorded coverage, and the count must not be shown as one. A marker that names a turn outside the transcript, claims to be current while stopping before the last answer, or carries an assumed flag for a part that is not behind a later answer, is rejected with 400.
- Every `document_evidence` entry stored by this build says how its text was read: `origin` is `ai_visual_transcription` (with `verified:false`) for a model's reading of a page or image, otherwise `source_extraction`. The server takes the pair from the file store when the process is submitted, never from the browser. An entry without `origin` was stored by an earlier build; Admin then says the reading was not recorded. `/api/knowledge/admin/document-source` returns the live source with the same `origin` and `verified`, and Admin shows the unverified note beside a transcription it reads there.
- A submission's `document_evidence` entry that was cited from a file removed or saved for later carries `retained_only:true`, `archived` and `disposition`; its file is listed in `documents.retained` (`{id,name,kind,size,sha256,archived,disposition,sources}`), not in `documents.documents`. `/api/knowledge/admin/document-source` serves only files in `documents.documents`; a saved excerpt is read from the stored `document_evidence` text. A file saved for later that is not cited is left out of the submission.
- `/api/knowledge/submit` answers 400 with `code:"document_citations_unavailable"` when cited file evidence cannot support the submission: a passage that cannot be read, or a part that rests only on saved excerpts in a new process, or in a revision when no earlier revision of that process holds the passage. `error` is one sentence that names the first file, the cited parts and the remedy; `citations` lists every affected file as `{document_id,name,state,source_ids,cited_by,more}`, where `state` is `removed`, `parked` or `unavailable`, `cited_by` names up to twelve citing steps, connections or notes and `more` counts the rest. Nothing is stored.
- `/api/knowledge/submit` with a `process_id` accepts `base_revision` (the revision the submitting copy was filed as; 0 when it does not know) and `acknowledged_revision`. When `base_revision` is sent and is not the latest stored revision, the answer is 409 with `code:"newer_revision_exists"`, `latest_revision` and `base_revision`, and nothing is stored, unless `acknowledged_revision` equals the latest revision. Neither field is stored. A request without `base_revision` is not checked. `/api/knowledge/status` also answers `latest_revision` for the process.
- `/api/knowledge/admin/delete`: `{submission_id,expected_revision,reason,confirm:"DELETE"}`. Available only when the server runs with `KNOWLEDGE_ADMIN_DELETE=true` (403 otherwise, and for anyone who is not an administrator); never in example mode. `expected_revision` must be the latest revision (the submission detail carries `latest_revision`). Answers `{deleted:true,submission_id,revisions,proposals,groups_for_review}` after removing the process with every revision and what was derived from it; see "Keeping and removing submissions" in KNOWLEDGE_GRAPH.md. `/api/config` reports the switch as `knowledge_delete_enabled`. `/api/knowledge/status` answers `status:"deleted"` (with `job_id:null`) to the holder of a deleted revision's capability.
- `/api/knowledge/submit` accepts what the Review editor accepts: a step's Input and Output and each Inputs / Outputs line up to 6,000 characters, Owner / role, System / tool and titles up to 1,000, and at most 400 transcript turns. A business object longer than 1,000 characters is stored with a label of 1,000 characters ending in "…" and its whole text in the entity's `data.full_label`. A refusal names the field and the limit ("Step S1: Input is longer than 6,000 characters.", "Inputs, line 3, is longer than 6,000 characters.", "A submission holds at most 400 transcript turns; this interview has 401.").
- Entity item includes data; relationship item includes evidence; proposal item includes exact evidence, but history is empty and history_count is provided.
- Group item has counts and empty members/aliases/history; use related pages below.
- Related submissions include metadata and ONLY cited user turns with `transcript_partial:true`. This is enough for exact excerpts; Open answer fetches submission detail for the full transcript.
- Related entities are metadata/label references only.

History/related kinds: `proposal,group,group_members,group_aliases,entity_neighbors,downstream`.
Response: `{kind,id,items,page}`.
- proposal/group: review-history records with the newest decision first (full records retained on subsequent pages).
- group_members: entity metadata (id/type/label/submission_id/revision/latest).
- group_aliases: `{alias}`.
- entity_neighbors/downstream: relationship metadata with `source_label,target_label`; confirmed cross-process relationships use `proposal_id` and `id` for opening proposal detail. Downstream follows reported sequence and confirmed handoffs, not mere containment or inferred effects.

Browse and related route states reflect the last source check. Resolving sources while filtering a page by status would move rows and could require an unbounded refill scan. Proposal detail, graph and review instead check only selected source evidence. Related pages include `source_verification:"stored_status"` and a visible `analysis_limitations` note directing the administrator to open a connection before relying on its source evidence.

Creating a reviewed group requires 2–100 current same-type entities. Corrections may remove members afterward, leaving a single member or an empty group; explicit revalidation still requires current retained members. Group mutations return metadata and counts without loading all members, aliases or history. `canonical-update` with `action:"replace_outdated"` exchanges each member that belongs to an earlier revision for the one entity of the same type and label in the latest revision of its process, leaves a member without exactly one such entity (or whose successor is in another group) in place, answers `replaced` and `left_outdated`, and is refused when nothing can be replaced. The group stays stale until it is revalidated.

Graph response: `{entities,edges,proposals,submissions,too_large,counts:{nodes,connections},message,analysis_limitations}`.
The `query` (label contains) and `type` filters narrow the entities of a view; Admin's Graph offers both (`type` at "All entities" only). Only latest revisions are graphed; selected submission_id restricts to one latest process and confirmed connections to relevant visible endpoints. Entities retain actor/system/evidence_turns needed for drawing but do not include full step bodies. Edges/proposals are graph metadata, without source quotes/history. A complete selected view exceeding 80 nodes or150 connections yields `too_large:true` and empty graph arrays with an explicit refine/select message, never a truncated partial graph. Process choices remain accessible through paged submissions. Full detail and every retained history/member/alias remain reachable through bounded routes.
