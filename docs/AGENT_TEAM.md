# Interview paths and agent responsibilities

| Entry point | Conversation | Background work |
| --- | --- | --- |
| Start talking, `VOICE_MODE=live` (default) | GPT-Live uses WebRTC for microphone audio, ordinary questions and speech. It can delegate complex reasoning to the lead model. | Final participant captions feed the coordinator. The team maintains facts, scope and workflow. The application controls review and completion. |
| Start talking, `VOICE_MODE=reviewed` | Each recorded answer is transcribed, then the foreground interviewer chooses a question. A reader plays approved text. | The concurrent service carries compatible facts and map steps forward. |
| Type instead | The concurrent service asks the next question using the written answer. | Uses the same facts, map and final review as reviewed voice. |
| Wrap up | The application checks the current evidence and requests explicit confirmation where eligible. | The process and coverage reviewers inspect the same evidence independently. |

## Roles and execution

| Role | Current default model | Responsibility | Authority limit |
| --- | --- | --- | --- |
| Lead interviewer | `gpt-6-luna`; configured process model for reconciliation and maps; document model for baseline rebuilds | Maintain the capture and ask one grounded question during information gathering. Also prepares working process-map updates on demand. | Cannot declare the interview complete by itself. |
| Coverage reviewer | `gpt-6-luna` | Independently assess all sixteen topics and every required dimension against participant evidence. | Can reject an overclaim; cannot manufacture missing facts. |
| Process reviewer | `gpt-6.1-terra` | Compare proposed actors, actions, connections, outputs and exception routes with their cited sources. Identify material contradictions or gaps. | Cannot rewrite source evidence or mark topics complete. |
| Document analyst | `gpt-6.1-terra` | Review authorized excerpts or visual sources on demand; audit document-supported map changes. | Documentary content is not confirmation of current practice. No arbitrary file access or file-management tools. |

[`agent_team.py`](../agent_team.py) supplies the immutable evidence snapshot, role contracts, execution events, provenance validators and completion permit. It does not call a provider or persist interviews. [`interview_orchestrator.py`](../interview_orchestrator.py) supplies bounded provider callbacks through the existing `OpenAIClient` in [`server.py`](../server.py).

Task-local settings or environment variables can override the four defaults with `AGENT_INTERVIEW_MODEL`, `AGENT_COVERAGE_MODEL`, `AGENT_PROCESS_MODEL` and `AGENT_DOCUMENT_MODEL`. The existing credential is reused; a separate key is not required for each role. Public configuration reports model identifiers, not the credential.

In live voice, GPT-Live asks ordinary questions while the managed interviewer maintains the capture. Typed and reviewed turns ask for one short foreground question and separately queue the full capture. New testimony, corrections, open gaps and volunteered issues guide question selection. Captured topics remain provisional until reviewed.

The lead returns changes to a private fact ledger rather than rewriting the entire memo on every answer. Application-assigned fact IDs preserve unmentioned details. Additions and explicit replacements or removals carry source references and a reason; a revision-bound schema separates edits to known details from resolving a gap. Public topic explanations are assembled from the retained facts. The ledger and its capabilities are not included in saved sessions or exports. A reopened session rebuilds from its full authorized evidence in one lead request. Typed and dictated answers, which are analysed in the background, continue the ledger of the conversation's own last capture; [CONCURRENT_INTERVIEW.md](CONCURRENT_INTERVIEW.md) describes how, and when a capture starts again from the transcript.

Each open gap or fact containing unresolved wording that the latest answer could affect — the answer or its question uses that topic's words, or shares two content words with the claim — receives an explicit reconciliation in that same response. Untouched claims keep their exact prior wording and need no row; the lead may still resolve one with an explicit operation when the testimony answers it. Keeping a fact requires a cited basis; changing it requires its exact targeted operation. There is no automatic removal merely because a new answer arrived. A single canonical citation list governs each edit. That same focus decides the model for the turn: a turn that touches an open claim uses the configured process model for reconciliation, because paired real prefixes showed that cheaper-model responses still retained stale uncertainty or inferred an actor from passive wording; a turn that touches none stays on the ordinary lead model. These are bounded evaluation findings, not a guarantee that every interpretation is correct.

A substantial new document baseline or long-history rebuild uses the configured document model in the lead role for that one request. Later changes use the ordinary lead model unless existing uncertainty needs reconciliation. Authoritative file revisions prevent a different search query from repeatedly triggering the expensive baseline route. This changes the model for one role; it does not add a second interviewer or an extra ordinary-turn agent call. The activity panel reports the model actually used.

The HTTP layer pins private fact citations through the current scoped document store. Selecting another excerpt from an unchanged file cannot silently erase an earlier cited fact. Those private citations are placed first in a notes request, across all files and ahead of saved excerpts of parked or removed files, so the excerpts the notes are built on are read again; a map request pins them too, after the map's own citations. One request reads at most 60,000 characters of file text. When the notes and the map together cite more, the document store still confirms each citation that did not fit as an excerpt of a file in this interview, without sending its text. The fact, finding or map component that cites it is carried forward, nothing may newly cite it, and the response's `document_reading.omitted_prior_sources` tells the browser how many cited excerpts were not read again. A map update returns each changed step or topic whole, with the sources it already had. When one of those is an excerpt the request did not read, the edit is taken only if it also brings a source of its own; otherwise that one edit is left out, the accepted component stays as it was and the rest of the update is applied. A restated connection that keeps such a citation is always left out, and so is the restatement of a step whose accepted handoff cites one, because a handoff is re-verified from quoted passages and an unread excerpt cannot be quoted. An edit that keeps an unread saved excerpt of a parked or removed file is left out even when it brings a source of its own: inactive evidence may preserve what already cites it and never supports a change, and the model cannot see that an excerpt it was not shown is inactive (when the saved excerpt fits into the request, the model is shown that, and an edit that cites it is refused as before). Each edit that is left out is named in the map's `open_questions`, which are returned with the map and sent back with it as the baseline of the next update; the working-map panel does not display open questions. The reading limit therefore does not refuse an update because of a citation that already exists; it can keep one edit out of that update. A citation the store cannot confirm is still refused, and a changed or removed source invalidates its old authority. The handler rechecks the same source selection before releasing a delayed response, map or draft.

When all sixteen candidate sections appear complete and document work is ready, the application returns one fixed acknowledgment: “Let me check that I have everything before we finish.” The browser displays it, or finishes playing it in voice, before requesting `/api/agent-team/review`. The process reviewer and the coverage reviewer examine independent copies of the same evidence concurrently. The coverage review itself runs as four concurrent topic groups (15, 17, 27 and 9 dimensions); each sees the whole transcript and every candidate finding but assesses only its own topics, and the merged result passes the unchanged whole-account validation. When the coverage reviewer repairs a section, the process reviewer's concurrent pass has read the lead's text, so it reads the repaired account once more before the result is published; a review without a repair makes no such pass. Code selects their grounded follow-up or the fixed final omissions check; there is no additional lead call simply to phrase that transition. The specialists' observations are fallible interpretations, not new source evidence.

| Transition | Provider calls |
| --- | ---: |
| Empty typed/reviewed opening with no documents | 0 |
| Ordinary typed/reviewed answer | 1 foreground question, background capture and separate map work |
| Advisory pre-check of newly captured topics | 1 coverage call in the background, display-only |
| Completion review after acknowledgment | 1 process reviewer + 4 concurrent coverage groups |
| Completion review in which the coverage reviewer repairs a section | the above + 1 further process-reviewer pass over the repaired account |
| Unchanged explicit final confirmation | 0 |
| Working-map update | 1 lead, plus a document audit when document evidence is present |
| Route recheck within a working-map update or draft | 1 further request, only when quoted route passages could not be verified |

After an ordinary turn that marks topics captured, the browser asks `/api/agent-team/coverage` to pre-check those topics in one call. The row shows “Captured” or “Captured · needs detail” if the pre-check found a gap. Opening the topic shows the gap and any suggested question. The pre-check applies to the exact captured answer. The completion review assesses every topic against the actual run and determines official coverage and the completion permit.

Notes and map generation run on separate queues. Draws and source checks also have their own workers, so the participant can see a diagram while its source check runs. See [Concurrent interview](CONCURRENT_INTERVIEW.md) for scheduling and cancellation.

Working maps use the configured process model. Standalone drafts use `DRAFT_MODEL`, defaulting to the configured process model, for generation, evidence audit and any required coverage assessment. Browsing the prepared fictional example makes no model request.

An empty start with no participant account or active documents uses a deterministic opening and no provider requests. Reviewers remain on standby: the interface does not claim that work is queued or reviewed before evidence exists.

A role can make several provider requests. The run status reports each role’s invocation count, actual request count, requested output ceilings and elapsed provider time. When the provider returns token usage, the status also reports input and output totals and how many requests supplied them. The run budget separately records reserved calls and output. Cancelling a run discards its results and releases its local worker and provider slot. The provider may still bill work it has already accepted.

## Evidence and official coverage

An `EvidenceLedger` encodes the context, chronological turns and authorized document sources, then hashes that snapshot into a revision. Accessors return copies. Duplicate source IDs are rejected. Assistant questions, document notifications and previous AI summaries do not become participant evidence. Archived or retained-only documents do not remain active evidence. Browser-supplied document evidence is discarded; the server retrieves the authorized scope itself.

The explanation test in [`interview_coverage.py`](../interview_coverage.py) is the governing standard: a section is covered only if a colleague could explain its relevant facts from the supplied evidence without filling a material gap by assumption. A tool name, a generic assertion of review, a polished memo or a long conversation is insufficient.

| Topic | What must be explainable |
| --- | --- |
| Name | Everyday name, the work it identifies, and other names or their explicit absence. |
| Purpose | The result delivered to the client or firm. |
| Trigger | Initiating event, who detects it, cadence and applicable deadlines. |
| Completion | Observable finish, required delivery or closure, and downstream boundary. |
| Accountability | The role accountable for the overall result, distinct from individual performers or reviewers. |
| Lifecycle | Items and stages, ordered actions and decisions, performers, systems and relevant locations, handoffs, exceptions and returns. |
| Checks | Actual checks, responsibilities, release conditions, failed-check rework and retained proof. |
| Variations | Applicable differences, changed work, reasons, effort, charging and constraints on removal. |
| Pain points | Manual work or friction and its practical effect, preserving attributed estimates. |
| Risk | Concrete failures and their consequences, rather than merely naming the person responsible. |
| Materials | Existing references, availability, location and whether they were reviewed. |
| Scope | Applicable clients, entities, jurisdictions, exclusions and boundaries. |
| Rules | Rules, sources, applicability and exceptions that change the work. |
| Connections | Dependencies, related processes and upstream/downstream handoffs. |
| Data and systems | Systems, data movement, ownership and reconciliation. |
| Volume and effort | Workload, frequency, effort and material differences. |

Each supported or non-applicable dimension needs substantive detail and participant evidence references. “Unknown,” “not asked,” “skipped” and “unavailable” are unresolved states, not reasons to mark a topic non-applicable. Non-applicability requires an explicit basis. The materials section may explain the reported inventory, location, availability and honest unreviewed state without requiring an upload. A mentioned document is never represented as read.

Managed completion review can explicitly repair a compressed candidate summary when the participant already supplied every required fact. It must publish the corrected answer, validated participant citations and `capture_repairs` metadata, with every dimension supported and no factual gap. This avoids asking the participant to repeat evidence omitted by the lead's summary. Legacy assessment remains demotion-only.

A repair replaces a section's text with the coverage reviewer's corrected section, so the application guards it rather than trusting it:

- Code refuses a repair of a partial or unknown candidate. It also refuses, and records as a gap that keeps the section open, a repair whose citations leave out a participant turn the section cited, whose text does not pass the wording guard the lead's own findings pass, or which contains a statement too long for the fact ledger. A refused repair leaves the lead's text in place. A repair that cites anything other than participant turns or intake context invalidates the whole coverage review, which the user can retry.
- The prompt, not code, tells the reviewer not to invent an actor, step or branch and to keep every supported statement in its existing wording. Code cannot tell a faithful shorter correction from a lossy summary, or a reported actor from an invented one. That check is the process reviewer's: when the coverage reviewer repairs a section, the process reviewer reads the repaired account in one further pass before anything is published. That pass receives the lead's findings with only the repaired sections' text and citations changed, not the coverage reviewer's status changes. The repair is applied only if that pass finishes and raises no material finding at all: a finding carries no section and cannot be matched with a finding of the first pass, so any material finding withdraws every repair of that review. A withdrawn repair leaves the lead's text published and the section in progress; `coverage_adjudication.withdrawn_repairs` names it, the published copy of the coverage assessment shows the section as open, the completion permit carries `repair_withdrawn:<section>`, and the private ledger is untouched. The published process review is then the pass that read the published text; the pass over the withdrawn text supplies no question for the participant, only `coverage_adjudication.repair_pass_findings`: what that pass found in the whole account with the repair applied, which may concern another section than the one the repair rewrote.
- A section left open by a refused or withdrawn repair has no reviewer question. The participant is asked about that section by name, and on the next turn the lead is shown the reviewer's proposed section (`proposed_correction`, with `findings_with_proposal_applied` for a withdrawn one) as a labelled proposal, never as evidence, so it can correct its own facts instead of waiting for the same proposal again. How reliably the lead does so has not been measured on the provider.
- A withdrawn repair is not requested again while the lead's text for that section is unchanged. The coordinator remembers a digest of the section text each withdrawn repair would have replaced (512 of them, in memory only). At the next review a section whose text has that digest is assessed in a coverage call of its own with the plain, demotion-only audit, whose schema has no repair: the reviewer judges the lead's text as it stands and either accepts it or records a gap with a question. So a repair proposed beside a finding that cannot be resolved (a detail the participant does not have) costs one withdrawn review, not one per review, and the following review reaches the question or the partial pause. A repair withdrawn because the review failed is not remembered; the explicit retry may still apply it. Once the lead changes the section, a repair can be proposed again.
- The lead's earlier text is kept. Each entry of `capture_repairs` carries `previous_answer` and `previous_evidence_turns`; the private ledger retires only the statements an applied repair changed or dropped (`superseded_review`) and keeps, as the lead's own facts, the statements the repair retained word for word. The memo panel marks a rewritten section, the completion notice names it, and the section's detail shows how many earlier statements survived and the notes before the review. Saved interviews and transcript exports keep that record.
- A draft has no process reviewer. A memo section the coverage assessment rewrites in a draft is marked partial, the draft's validation notes name it, and the report and memo editor show the earlier wording, which the editor can restore.

Repairs are still whole-section rewrites proposed by a model. Expressing a repair as explicit per-statement operations chosen by the reviewer, and measuring on real completion reviews how often a repair fires and how much it shortens a section, remain open.

Question selection should follow the most useful remaining gap, preserve volunteered second issues, and avoid repeating facts or precise details the participant cannot provide. A local “No” answers its local question; it does not close the whole interview. Unavailable details remain visible gaps while the interviewer explores answerable and untouched sections. An explicit request to stop preserves a partial account without another probe or a completion claim. Only a direct request counts (“I need to stop now, my manager is calling”, “Sorry, can we pause? I have another meeting”, “Let’s stop here and continue tomorrow”); an answer that merely begins with “stop”, “pause”, “let’s finish” or “I’m done with this when…” and continues with the account, or that stops a thing in the work (“stop the call”, “we need to stop the session”), is analysed as an answer. A stop is answered once: after the acknowledgement, **Wrap up**, **Skip** or a file follow-up is handled normally instead of repeating it.

The process reviewer checks the candidate account against the participant transcript and authorized sources, including the basis for actors, handoffs and exceptions. The separate workflow source audit checks the graph itself. A positive process clearance requires an explanation and citations.

## Completion belongs to the application

`completion_permit` requires successful reviews of the current evidence across all sixteen topics and a process review with no material blocker. Each topic must be covered, explicitly inapplicable, or ready for owner review with its remaining questions accounted for. A reviewed owner follow-up keeps the underlying fact open. It records the affected scope, what proceeds or waits, the role or source that can resolve it, and supporting participant statements. Pending document review also prevents a final check.

Only after those requirements are satisfied can the application ask its global final omissions check. Full completion additionally requires an explicit participant response to that actual check. “Yes” to whether anything remains means there is more to add. A local “No,” an answer with a new correction, a stale result or a replacement clean assessment cannot satisfy confirmation. New information is reviewed again.

What counts as that response is decided by two wording rules in `agent_team.py`, both about content rather than about listed sentences. `FINAL_CONFIRMATION` reads the reply as parts: fillers, negatives and statements that nothing is missing, then a closing courtesy (“No, I think that's everything”, “Not that I can think of”, “Um, no, nothing else, thanks”). A “yes”, or anything that goes on to say something (“No, but…”, “Nothing else, unless…”, “That's it for the approval step”), is not among the parts and confirms nothing. `reply_adds_nothing` is true for a short reply made only of words of the conversation itself (yes and no, courtesies, first and second person, auxiliaries, verbs of thinking and saying); one word that could name a thing, a person, an action, an amount, a time or a condition of the work, a number, an acronym or a long reply is content. The coordinator (`_reply_step`) uses them as follows, each time without a provider call:

- a confirmation completes the account; “yes” asks “What should we add to the account?”;
- any other reply that adds nothing (“Okay.”, “Thank you.”, “What do you mean?”, “There is something else.”) has the final check asked again from the review that passed, once with the hint “Say “no” if nothing is missing, or tell me what to add.”; it never confirms;
- a request to stop in reply to the final check pauses like any other request to stop and confirms nothing, but the review is kept: **Wrap up** (or the next reply that adds nothing) returns to the same final check, and an explicit “no” then completes the account without a second review;
- after the completion line the account stays complete until the participant adds something: a thank-you, a goodbye, a request to stop and whatever the spoken interviewer says in between are answered with the same capture, marked `completion_retained`, and the browser neither shows nor speaks its line again; in Live voice the ending that is due nine seconds after the line is left in place, and words that are still being judged when it is due are waited for;
- an acknowledgement of a partial pause (“Okay, thanks.”, “Sounds good.”) keeps that pause;
- a reply with content is analysed by the lead and reviewed again, exactly as before.

In Live voice, a trailing interviewer caption can arrive while the application prepares or runs the review. The review keeps the original transcript, document selection and participant answers. The application accepts the result when those sources still match. If another interviewer remark follows the final check, “No, nothing else” can still confirm the account. A bare “no” after an intervening question prompts the application to ask the final check again.

While the final check waits, the Notes panel offers **Nothing to add** beside “Waiting for your final confirmation.” It sends “No, nothing to add.” as the participant's own reply.

Process findings also conservatively reopen the published lifecycle status so the visible topics do not imply universal coverage while a material route remains unclear.

Review failures preserve the capture and block completion. Participant confirmation, topic coverage, draft availability and process-owner approval are separate states. A partial draft may be useful, but is not a completed interview. See [interview completeness](INTERVIEW_COMPLETENESS.md) and [memo requirements](MEMO_REQUIREMENTS.md).

Opaque capture tokens and review tickets bind saved state to the actual evidence, context, authorized sources and issued final check. Ordinary capture and review tickets expire after thirty idle minutes. An issued final check or completed account stays available for four hours, subject to the bounded registry. The cache is ephemeral. Duplicate review requests share one in-flight execution; an explicit failed-review retry retains the successful lead capture. Unchanged final confirmation reuses successful assessments. New substantive facts, changed source contents or authorization, cancellation and superseding requests invalidate stale authority. Source retrieval retains the original query for known non-evidentiary acknowledgments and confirmation while rechecking current document access and contents.

This is whole-account freshness, not an assertion that unchanged citations prove every topic is unaffected by a new answer. A correction about who reviews a file can affect lifecycle, checks and accountability. New candidate facts therefore remain awaiting review until the next completion review. Previously captured explanations still guide the lead so it does not ask the same questions again.

An application-checked unavailable-only pause is possible without pretending the interview is complete. Every open topic must have actual participant evidence of unavailability, specific unresolved dimensions and no useful remaining question; material process findings must also be tied to that evidence and have no answerable question. An untouched topic, missing audit, pending document or blank reviewer question alone does not establish unavailability.

When only explicitly unavailable topics remain, the acknowledgment is “Let me check what we have and keep the unanswered parts open.” That partial review cannot authorize full completion. Typed review offers Pause and Resume; cancellation and retries preserve the account while invalidating obsolete review authority.

These checks enforce source identity, structure, freshness and the completion contract. They cannot prove that a model's confident interpretation of a valid citation is correct. Independent semantic review and task-specific evaluation remain necessary; Structured Outputs constrain a response's shape, not its truth. [OpenAI Structured Outputs guidance](https://developers.openai.com/api/docs/guides/structured-outputs).

## Documents join when needed

The existing document pipeline owns uploads, originals, extraction, source locations, scoped retrieval and review phases. The analyst receives only that authorized material. Text observations cite permitted chunk IDs; supported visual inputs use the relevant supplied page or image. Text-only analysis cannot invent a new visual transcription. File instructions are treated as source content, not instructions to the agents.

Mentioning a document is distinct from reviewing it; reviewing it is distinct from confirming that people follow it. Conflicts between a procedure and the participant's account remain explicit. The analyst can suggest a useful question, but only the lead asks it. A workflow containing document evidence receives a separate source audit. Working-map updates remain provisional and do not authorize interview completion.

The team has no autonomous folder scanning, moving, renaming, deleting, publishing or messaging capability. Existing user-driven file actions and persistence remain in the application. See [document interviews](DOCUMENT_INTERVIEWS.md).

## Activity interface

[`web/agent-team.js`](../web/agent-team.js) renders real server execution metadata in the Interview team panel, a short status beside the Workspace title that opens into the role list. It stays off the page until a role has run. The three core cards are present; the document card appears when analyst activity is supplied. Queued, working, done, waiting and issue states come from actual run events. The view does not invent timed milestones, percentages, reasoning traces or evidence of a successful review.

Cards disclose their responsibilities and bounded status details. Completed reviewer cards explicitly say that a finished check can still leave open topics. Recent completed work contains at most three actual completion events. Older polls and retired runs cannot overwrite a newer display. Collapsible native controls, polite status announcements, narrow-screen layout and reduced-motion styling are implemented. This is an implementation description, not a completed assistive-technology or visual acceptance audit.

During ordinary turns, the Notes headline, its bar and the Workspace count on narrow screens count captured and not-applicable topics. Every counted topic has a solid circle. The completion review adds a tick to confirmed topics and marks the figure “Checked”. A new answer withdraws the ticks and “Checked” while keeping the capture count. Below the topic list the panel shows one status line at a time, giving priority to trouble, then work in progress, then what the notes include. The next action appears above Wrap up and Create draft. Completion-review waits say “Checking the recorded topics and process…” in both typed and voice status. The interface identifies reused results as prior work.

## Live voice (`VOICE_MODE=live`)

GPT-Live listens and speaks over WebRTC. It chooses ordinary follow-ups from the conversation. Background capture tracks the participant’s account and sends compact coverage progress when the participant has paused. Specialist question suggestions do not script the next spoken question.

1. Each final participant caption schedules one background lead call (`/api/agent-team/interview`, 400 ms debounce, one in flight; a newer answer queues one follow-up). A capture that returns after the participant has answered again, or while they are speaking, is not thrown away: while every answer it read is still in the transcript unchanged, its notes and capture token are applied with a coverage checkpoint bound to the answers it read, nothing is reported to GPT-Live for that lagging checkpoint, it carries no completion authority (no verified coverage, no acknowledgement, final check, pause or completion line), and the follow-up capture for the newer answers starts at once. A capture that read an answer which was later corrected or removed is discarded. One that read a live caption which has since gone on (words added at its end, while the answer is still spoken or after a pause, when the same caption resumes) is applied the same way, as notes only: its capture token is not taken, its process leads are not kept, and only a capture that read the answers exactly as they stand marks the latest one as captured. A long answer does not wait for its end. When the answer being spoken passes 1,400 characters (the server's limit for the quick excerpt capture, about 95 seconds of ordinary speech) or 100 seconds, or answers that already ended still have 200 characters missing from the notes because the participant went straight on (the November 19 case: an 18-second answer, then a 71-second one 2.4 seconds later), the transcript as it stands is captured while they keep talking. One capture at a time, at most three per answer, the first, second and third at least 30, 60 and 120 seconds after the previous notes capture of the voice session returned, if one has (an answer that already ended is captured at once the first time); not after the final check was asked, a completion or a review, and not while the words so far could be read as a request to stop. That check (`liveStopInWords`) splits as the server does, at . ! ? … ; and line breaks and then at commas, colons, brackets and dashes, and holds the capture back while a clause that is a request to stop on its own (the stop patterns the server gives the page) is among the first nine clauses or in the last three sentences. It reads the patterns as Python does (`pythonStopPattern`): `\w`, `\d`, `\s` and `\b` take in every language's letters, digits and spaces, and İ, ı and ſ match i and s ("another café meeting", "İ need to stop"). It is broader than the server, which reads such a request among the first clauses after fillers, courtesies and reasons ("Okay", "Sorry", "my boss is calling me") or in the last sentence; the last three sentences leave room for a goodbye after it (`tests/fixtures/live_stop_cases.json`, held to `server.stop_request_prefix`). The page sends this capture with `live_partial: true`. The server then leaves the capture the page holds valid, does not claim its capture family (it runs beside it, and the next capture that claims the family retires it), opens no review, issues no capture token and publishes no ledger: the capture of the whole answer continues from the last whole-answer capture as if the partial one had not been taken, with the same model call (the excerpt or incremental path, the previous capture's context, the same excerpt budget). Its facts quote a caption that is still growing; `capture_facts.rebase` would retire every one of them once it grows, so they are shown and never kept. The server refuses `live_partial` that is not a boolean, without `live_notes`, on any action but an answer or on its own background work (400), and a partial capture whose words read as a request to stop or as a reply the held capture would answer (409, before any model call). On the page it is applied like a lagging capture: its process leads are not kept, nothing is sent to GPT-Live for it while the participant speaks (if they pause on exactly the words it read, the ordinary progress note for those words goes), and while voice is on it never marks the answer as captured (once voice has ended, one that read the words exactly as they stand counts as the catch-up). A capture sent when the participant paused, after which the same caption went on, reads part of the answer in the same way: it counts toward the answer's three, and the answer is treated as one whose speaker goes on after a pause. When the capture of the whole answer is due (no caption open, the microphone quiet; while the microphone still hears sound after the caption finished, it is tried every 400 ms) and one that read only part of the answer is on its way, that one is cancelled and the capture of the whole answer is sent (it could never mark the answer as captured), unless it is nearly back: on its way for three quarters of the time the last capture of its kind took. It is then waited for until a quarter past that time, its notes are applied, and the capture of the whole answer goes the moment it returns, or when it is overdue, in its place. An answer that is already long (1,400 characters or 100 seconds) is captured when the interviewer begins its reply, or 3.5 seconds after its last words; one whose caption already went on after a pause, when the interviewer replies or 10 seconds after its last words (later words start a new caption, `web/live-voice.js`), so a thinking pause is not taken for its end. An ordinary answer is captured 0.4 seconds after its caption finishes, as before, and so is every answer in the closing sequence; with the caption check on (the default, see below), the end-of-answer capture also waits for that answer's check: if the check has not settled 0.4 seconds after the caption finishes, the capture goes 0.4 seconds after it settles or after its six seconds, so at most 6.4 seconds after the check began, and an answer that is already long goes at its own time above or 0.4 seconds after the check settles, whichever is later. Its cost is that of one capture, as before, unless the check's result arrives after those six seconds while voice is on: the capture that read the caption is then redone, one more notes capture. The notes line says "Notes include part of answer N" (or "of M" once a later answer has begun) while the notes hold part of an answer; while voice is on it is busy only while a capture is on its way or about to go, and otherwise only says what the notes hold. Its fact transaction updates the notes, the coverage checkpoint and the advisory pre-check; its question is **not** spoken or added to the transcript. The ledger tolerates GPT-Live's own caption as the assistant turn after a capture.
   Participant captions use a local microphone check (introduced in 0.24.1). The transport strips the transcriber's stream markers and drops a fragment whose session-timeline window held no measured microphone energy. Over silence the input transcriber invents fragments ("a young woman", "a person is"); before this filter each one became a transcript turn, a lead capture and a notes update. The filter acts only on positive evidence of silence, and never silently. A separate long analyser on the microphone (about 0.7 s of audio, read in 21 ms sub-frames) is read at every display frame, every 250 ms in a hidden tab, and again at the moment a fragment is judged, so each reading covers all the audio since the previous one; a sub-frame counts as speech when its RMS is at least 0.008 (the level that has always counted), or at least 0.002 and twice a running noise floor (which follows quieter audio at once and louder audio over about eight seconds). The noise floor therefore only makes the gate more sensitive for quiet microphones; a loud room or a long steady voice can never turn speech into measured silence. A fragment is withheld only when its whole window (1.5 s either side, between the start of the session and now) was measured without a gap and held no such energy. Whatever could not be measured is kept: no timestamps, suspended audio, a window ahead of the local clock, or a hidden tab whose timers the browser slowed beyond the analyser's reach. In longer calls the provider audio clock can advance faster than the browser clock. The gate corrects the offset when a caption's end would otherwise fall after receipt, keeps the correction across delivery delays, and treats implausible timestamp jumps as unmeasured. A withheld fragment is not discarded: the transport hands it to the application (`onWithheld`), which keeps it apart from the transcript for the interview and lists it, read-only, above the conversation in “Speech not captioned (N)” (in every view of the interview); nothing is put back into the transcript from that list. An information notice (“Some speech may not have been captioned: “…”. Check your microphone level, then say it again or type it. …”) is shown for each withheld moment that holds four words, and once per live session when short moments have been withheld three times; words heard while the participant had muted the microphone are kept but neither listed nor announced. The gate's levels and how often the transcriber's inventions raise the notice need validation with a real microphone and the real service.
   Fund terms and configured names in participant captions are then corrected using the participant's own audio (`LIVE_CAPTION_CHECK`, on by default). The live transcriber takes no spelling hints, so in the November 19 stress test "KYC" was captioned "kite" and "LPAC" "CPAC", and notes must quote the caption as it is; dictation, with the hints, got the same terms right. The transport keeps the microphone the live session already opened (echo-cancelled) as 16 kHz 16-bit mono for the last four minutes, through an audio worklet from this origin (`web/live-voice-tap.js`, which hands over a block of about 100 ms at a time) or, failing that, a script processor whose buffers are stamped by the audio clock (a busy page delivers them late, several at once); the audio is low-passed at 7 kHz before it is taken down to 16 kHz, so sound above 8 kHz does not fold into the speech band. Nothing is kept while the participant has muted the microphone. When a participant caption becomes final, its session-timeline window is mapped to the page clock from the arrival of the participant's words: the largest lead after the one or two largest of the last two minutes are set aside (one timestamp that is too late never moves every later window), and never less than the caption's own last word requires, so a provider clock that runs far ahead (3.4 s two minutes into a real session, more than the speech gate accepts) moves the window back and never costs the check its audio. The words arrive some time after they were said (0.7 to 0.9 s in a real session), so the window falls late by that delay; it is padded by 2 s before and 1 s after, and that audio is sent as a WAV file to `/api/transcribe` marked as a caption check (`X-Transcription-Purpose: live-caption-check`, the only value accepted, and only where the check is on). For that request alone the server's glossary is the whole of the spelling hints: the fund terms of `SPOKEN_FUND_TERMS`, the process name when it is a short plain term (the page's only hint) and `TRANSCRIPTION_KEYWORDS`, never a term from the transcript (a caption, or another check's reading, may be the mishearing). Like dictation's hints they are at most 30, the twelve fund terms first, so with a process name only the first 17 configured keywords are used (18 without one). The answer names those terms and the mishearings `SPOKEN_FUND_TERMS` lists for them ("kite" for KYC, "CPAC" for LPAC, "DI" for IRR, "K one" for K-1). Dictation and reviewed voice are sent and read exactly as before. The reading is never used whole. In a real browser session (2026-11-20) the readings fixed "K one" (K-1), but for words the caption had right they wrote "Instruct" or "I reconcile" for "We reconcile" and "Investron" or "Investor" for "Investran", and lost "pack" after "LPAC". The first run of that session sent no audio; its captions of the same clips had "Calc" for KYC and "LP AC" for LPAC, and the tests pair them with the second run's readings. Instead, the reading is aligned word by word with the caption (case, punctuation and hyphens aside, "one" to "ten" as digits), and unless at least 60% of the caption (by letters) is matched nothing is used. Between two matched words, where the two differ, the caption's words are replaced only when the reading there is exactly one glossary term or its plural (for a listed mishearing, also with common words beside it), written as the glossary writes it (with a capital first letter only where the reading begins a sentence), that the caption does not already have there in any form, and either the caption has one word there that may become the term ("kite" becomes KYC), or caption words next to each other spell it with only spaces or hyphens between them ("LP AC pack" becomes "LPAC pack", "K one" K-1, "K ones" K-1s; "the LP. AC members" stays), or the reading lost a word beside the term and just one caption word there is a listed mishearing of it ("CPAC pack" read as "LPAC" becomes "LPAC pack"). The same holds where the reading has the term with only common words beside it: just the one listed mishearing becomes the term, and the common words are not added ("DI and the DPI" read as "The IRR and the DPI" becomes "IRR and the DPI"; in a real session on the merged build "DI" was missed because the reading had two words there). A caption word may become a term only when it is not a common word, not a glossary term or its plural (the caption heard a term: "LPA" never becomes LPAC, "NAVs" never NAV, "distribution" never a configured "Distributions"), and not written as an acronym unless it is a listed mishearing of that term ("GP", "TVPI" and "IR" stay; "CPAC" and "DI" do not). Where each caption word there is read as one other word ("kite CPAC" as "KYC LPAC"), each is judged by itself. The term takes the caption word's place and punctuation. Every other difference keeps the caption's words, and so does any difference before the caption's first matched word or after its last, where the audio may be cut or run into other speech. A common word is never turned into a term on its own: "each side letter" read as "ACH side letter" stays (the price is that "each or SWIFT" for "ACH or SWIFT" stays too). The turn changes only when a term was corrected; the result must also not end like a request to stop and must fit the transcript limits. The end-of-answer notes capture and the map wait for the check, at most six seconds from when it began; while voice is on, a result after that corrects the turn like any other change, so the capture that read the caption is not used and the capture is redone. A process lead already offered to GPT-Live stands: the answer's words it was offered with, and its quote of them, take the checked wording, so `sendLiveLead` does not read the corrected term as the participant correcting themselves and sends no "lead is outdated" note (where a corrected word runs across the end of the words it was offered with, the lead is withdrawn as before). When the check settles, fails or passes its six seconds, the capture that waited goes 0.4 seconds later if no participant caption is open (an answer that is already long waits as described above); while the microphone still hears sound it is tried every 400 ms, as after any capture. Once voice has ended a result is used only within those six seconds, and the map owed for the last spoken answer is drawn from it; after that the check is given up, so the catch-up, Wrap up and a draft read the transcript as it stands. A capture taken mid-answer waits for the check in the same way (in a real session one read an answer 0.6 s before its check corrected it, and its result was thrown away), and goes when the check settles or with the next words of the answer being spoken; a capture that waited does not use up one of the answer's three. A caption that goes on after a quiet checkpoint keeps the corrected wording of its words so far, and once it is final again only the words added (from their first fragment's audio) are checked. Everything uncertain keeps the caption exactly as it arrived: no timestamps, no tap, a caption over 150 seconds or of one word, audio missing inside its window, a request that fails or is refused (no retry, nothing said to the participant), a caption that changes meanwhile (the stale request is cancelled and the words not yet checked are checked once it is final again), and the closing sequence. Replies to the final check, requests to stop and what follows the completion line are decided on the caption and are never checked; once the closing sequence, Wrap up or a draft begins every check is given up and none waits or is sent. At most two checks run at once. The raw trace records each check (`live.caption_check`: sent, replaced with the number of terms corrected, kept with the reason (`same`, `no_correction`, `misaligned`, `empty`, `no_terms`, `too_long`, `stop_phrase`, `limit`), discarded, failed or skipped, with word counts and no text) and whether the tap started (`live.caption_tap`). With `LIVE_CAPTION_CHECK=off` the page records no audio and sends nothing.
2. After a completed capture (and on connection), one short silent note reaches GPT-Live as a single `session.thinking.append`, a progress note only ("Private capture status; silent, no speech requested. Notes cover the current N participant answers. Still open: … These are provisional coverage labels, not questions or a topic order. Follow the conversation; do not react to this update."): the keys of the topics still open, bound to the exact participant text that was analysed and trimmed to one context event. It is held while a participant caption is still in progress and sent when they pause. It carries no suggested question and no reviewer gap wording; what each topic key needs is named once in the static live instructions (`live_topic_guide` in `server.py`). Until 0.26.1 the note also carried "When they finish, I ask: …" with the lead's or reviewer's suggested question; that was removed because it caused repeated and wrongly anchored questions (see CONVERSATION_REPAIR_QA_2026-11-05.md). The live instructions forbid any self-initiated wrap-up and state that it speaks only as the interviewer. Caption fragments send nothing. The 0.24.0 update carried all sixteen findings as JSON in about fourteen chunks and was repeated for every caption fragment; fed that stream, the live model drifted into voicing the participant's side of the conversation, which a participant heard as the voice repeating everything they said; even a four-chunk update landing mid-answer made it finish the participant's sentence.
3. When the lead requests a completion review, the application records the authorized acknowledgement in the transcript and asks GPT-Live to read it through `session.instructions.append`. The review starts automatically once the command receipt and a final caption matching the whole line have both arrived. They may arrive in either order. If delivery fails or the twenty-second wait expires, the acknowledgement stays on screen and the participant can select **Continue completion review**. An intervening correction withdraws the old review.
   The transport recognizes the reading from its words and tags it with the command’s event ID. The application omits these tagged captions to avoid recording the same line twice. It keeps other interviewer speech and participant interruptions in order. Ordinary application-issued lines wait up to fifteen seconds for a receipt or a recognized reading. Following the final check, a courtesy reply preserves the completion and an addition reopens it. The ending allows time for playback and for the participant’s last words.
4. The working map starts alongside each capture, as in typed mode.
5. Voice can end while this work is still running (**Stop talking**, a session the provider closes, the transcript limit). The work is finished, not discarded. A completion review that is running when voice ends keeps running: the page shows the ordinary busy state with “Checking the recorded topics and process…” (and **Pause review**) until it settles, and its decision is then applied as in a typed interview, as text and without the ended voice session. Stopping adds nothing to the transcript, so the review still matches the conversation it checked. If the result cannot be applied (the review failed, or the conversation changed while it ran), the participant is told and **Retry completion review** is shown: after a failure it repeats the prepared review without a second capture, and after a change it runs the completion check on the conversation as it is now. If the participant's last words reach the transcript while voice is ending, they withdraw the check; the participant is told once and **Wrap up** runs it on the whole conversation.
   The notes capture is treated the same way. A capture that is on its way when voice ends is awaited, and when it returns for the unchanged participant account its notes are applied and nothing else: memo, capture token, coverage checkpoint, never as a verified review; its question is not shown, nothing is spoken and no review starts (a result that only repeats an earlier capture does not replace that capture's token). When the transport has delivered its final captions and the notes still lack the last spoken answer (its caption was only finalized by the stop, or the capture on its way began before the last words and was cancelled), one catch-up capture is sent to the same lead endpoint. While either runs the page is busy with “Updating notes from your last answer…” (the lead's proposed question is never shown there), so **Create draft**, **Wrap up** and **Continue talking** wait for the notes, for at most ninety seconds: a capture that has not returned by then is given up and reported like a failed one. If the catch-up fails, the participant is told, the Notes panel reads “Notes are behind the transcript” with **Update notes** (the same capture again, on request), and the map's “Up to date” is not repeated on the notes status line; typing an answer, Wrap up or more voice also bring the notes up to date. Stopping when the notes already include the last answer sends nothing. A live capture also advances the notes line, which now reads “Notes include all N saved answers” after each capture instead of “Updating notes for answer N”, and “Notes kept through answer N · paused at your request” after a pause reply, which carries no notes.

GPT-Live's words are not authority: completion still requires the application's permit, and an interviewer line it improvises is ordinary transcript text. What is given up relative to reviewed turns is the pre-audio content gate on ordinary questions and the exact-transcript verification of playback. `VOICE_MODE=reviewed` restores the reviewed-turn voice below.

## Reviewed voice (`VOICE_MODE=reviewed`)

The reviewed team voice uses this sequence:

1. Browser microphone capture produces a recorded answer segment.
2. `/api/transcribe` returns text, which is added to the participant transcript.
3. The concurrent interviewer selects a question and queues evidence capture. Wrap-up synchronizes the current evidence before specialist review.
4. The browser verifies `speech_authorization`, matching approved text, completion flags and the unchanged source snapshot.
5. The selected reader plays that approved response; listening resumes after playback finishes.

[`web/controlled-voice.js`](../web/controlled-voice.js) uses local speech activity detection with a 1.8-second silence interval (`VOICE_PAUSE_MS`, 1000–5000 milliseconds; a longer pause adds the same time to every reply) and a capture bound that runs from the first speech, not from when listening began: after 90 seconds without a pause the participant is told and recording continues to the pause; after a second 90 seconds that part is saved and transcribed while the rest is recorded as more of the same answer, so the interviewer is never asked about half an answer. A recorder in which nothing has been said is replaced every 90 seconds without any request. The end of a turn is shown on screen (“Thinking… keep talking if you weren’t finished”) and the microphone stays open while that answer is transcribed and its reply is prepared: speech that resumes in that window joins the same participant turn, a reply already requested for the first part is cancelled, and the interviewer is asked once more with the whole answer. A transcription already under way is kept, not repeated. A noise gate keeps coughs, breaths and the echo tail of playback from becoming paid, empty transcriptions: a segment is transcribed when it holds a quarter second of voiced audio, or about half that when its loudest moment is clearly speech (so a one-word answer such as “No.” is kept); the short decay after the last voiced moment counts. Anything less is dropped locally without a transcription request. A near miss shows “I didn’t catch that. Please say a little more.”; a click or a breath is dropped without comment. A transcription that returns no words keeps the microphone listening with a short notice; only three empty answers in a row stop the session. The reader's short-lived token is requested while the lead is still working, so approved playback can start as soon as the response is authorized; a token older than forty seconds is replaced. Silence alone does not create transcription requests. The level meter does not depend on animation frames: a hidden page is metered by timer, a visible one has a timer behind each frame, and a reading that comes late measures the two thirds of a second before it in 21-millisecond blocks instead of counting the gap as speech or as silence, so an answer given while another window is in front still ends and gets its reply (about a second later than on a visible page). A silent recording that includes three seconds or more that no reading covered (a frozen or sleeping page) is restarted with a notice that listening had paused; it is not sent for transcription. Capture closes when an approved reply is about to be played and stays closed during the opening question, the completion review and playback. Mute, stop, page exit and failed operations clean up recording and pending work. While the app holds the microphone closed, the microphone button reads “Mic paused while I speak” (or “…while I think”). A recording in which speech is heard within 150 milliseconds of the microphone reopening began before the app was listening: it is not transcribed and the participant is asked to say it again. To avoid turning away someone who habitually starts early, a second early start in a row, or one followed by more than ten seconds of speech, is kept with a notice that the beginning may be missing. This is turn-based voice, not simultaneous full-duplex conversation or spoken barge-in. Review latency is therefore part of the participant experience.

Natural playback uses `gpt-realtime-2.1-mini` as a text reader, with no interview tools and a short-lived client credential. The project API key stays server-side. Audio is buffered before playback; the provider's returned speech transcript must match the approved text after Unicode normalization, case folding and removal of non-letter/non-number characters. A mismatch withholds audio. This checks the returned transcript, not independent acoustic verification of what the speaker emits. Installed computer voices are also available through browser speech synthesis.

The specialist models do not speak directly. Stale, cancelled, malformed or unapproved controlled-voice responses are not applied or played. Review and playback failures retain already accepted transcript text, but audio that failed transcription cannot be claimed as a saved answer. Physical microphone capture, sound quality, real interruptions and end-to-end spoken latency still need a hands-on test.

The HTTP `/api/live-session` route creates a GPT-Live session only in live mode; in reviewed mode it rejects the request with status 409 before provider work.

Both `/api/interview` and `/api/agent-team/interview` route through the authoritative coordinator for the application's OpenAI client and its subclasses. Older text clients therefore receive the same completion gate. Isolated test adapters can still be injected at the server boundary; no browser parameter selects or weakens that adapter.
