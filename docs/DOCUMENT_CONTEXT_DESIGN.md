# Document context during an interview

Design recorded: 2026-11-02; upload coordination updated for 0.19.0 on 2026-11-03. Official documentation snapshots are in ignored `work/docs-*.md`. This document records the chosen architecture and its evidence boundaries. [Build verification](BUILD_VERIFICATION.md) separates executed checks, historical provider evidence and unverified physical audio.

The interview remains the participant's account of the business process. An uploaded workbook, PDF or image can establish documented notes and workflow steps through exact cited excerpts and an audited baseline. It cannot create participant testimony, confirm current practice, establish owner approval or announce that the interview has enough detail. Documented evidence and participant confirmation remain distinct.

## Research and choice

| Official capability | Consequence for this application |
| --- | --- |
| Responses `input_file` accepts files directly. Vision-capable models receive PDF text and page images. Each file must be under 50 MB, with a 50 MB combined request limit. | Useful for an individual visual page, but sending every original in every conversation request is not the storage or retrieval strategy. [OpenAI file inputs](https://developers.openai.com/api/docs/guides/file-inputs) |
| Direct spreadsheet augmentation parses at most the first 1,000 rows per sheet and supplies summaries/header metadata. | A successful direct-file request does not establish that a 50-tab workbook's later rows were read. Preserve and index the complete accepted workbook locally. [Spreadsheet augmentation](https://developers.openai.com/api/docs/guides/file-inputs#how-spreadsheet-augmentation-works) |
| File Search offers hosted semantic and keyword retrieval over uploaded files in vector stores. | A future option for larger text corpora. Retrieval is not a workbook calculation engine or proof that every row participated in an aggregation. [File Search](https://developers.openai.com/api/docs/guides/tools-file-search), [Retrieval](https://developers.openai.com/api/docs/guides/retrieval) |
| OpenAI recommends Hosted Shell for spreadsheet aggregations, joins, charting and custom calculations. Hosted Shell executes in managed containers. | This feature captures business context rather than performing arbitrary workbook analytics. Neither Hosted Shell nor model-directed local shell execution is implemented. [File-input guidance](https://developers.openai.com/api/docs/guides/file-inputs#how-it-works), [Hosted Shell](https://developers.openai.com/api/docs/guides/tools-shell#hosted-shell-quickstart) |

The selected design combines persistent local originals, a complete bounded text index, an early relevance assessment, and an incremental review. The conversation pauses while that review finishes; early findings remain in Assets rather than triggering intermediate conversation. Bounded review requests preserve progress and respect provider limits without implying coverage that spreadsheet augmentation does not provide. The local 64 MiB upload limit is an application storage limit; it does not override any provider request limit.

## Ingestion and source coverage

`documents.py` stores the original before parsing, with a SHA-256 digest, immutable upload context and a scope-bound document ID. Extraction runs separately from upload. SQLite FTS5 holds text chunks and source locations; a transaction publishes the extraction result. Limit failures do not silently publish a truncated text index.

One full-text table serves every interview, and FTS5 can find rows only by `MATCH` or by rowid. Store format 2 therefore keeps `chunk_map(scope, document_id, id, chunk_rowid)`, an ordinary table written in the same transactions as the full-text rows: paging through a file's sections, counting them, opening a source, resolving earlier citations and replacing a file's index all find their rowids there. A search by words is matched inside the interview (`scope` is an indexed full-text column, and the expression is `scope : "<digest>" AND {label text} : (...)`), so its cost follows the interview's own files, not everything ever uploaded. A store of format 0 or 1 is rebuilt once, in one transaction, when this build first opens it (same rows, same rowids); builds that know only format 1 then refuse it, as `docs/DESKTOP.md` describes. `DocumentService.supporting_context` remembers its last eight selections for as long as no record of the interview's files has changed, so the several identical retrievals of one turn or status poll are computed once.

- **PDF:** inventory every accepted page. Extractable text is split without dropping a long page's tail. Source IDs retain page numbers. Pages with no extractable text, or whose text decoding fails, receive an explicit visual-review placeholder rather than a claim that their contents were read. Pages with detected visual content retain the indexed text and a separate visual-review source. Inventory records which pages still need that review.
- **XLSX/XLSM:** inventory every worksheet, including hidden tabs, and index populated cells throughout all accepted rows. A 50-tab workbook and rows beyond 1,000 are within this design; the configured maximum is 100 sheets. Retain sheet names, row intervals and cell ranges. Read formula text and available saved values without recalculating formulas, following external links or executing macros. Missing cached results and chart-only tabs remain explicit limitations.
- **CSV:** index accepted rows and coordinates throughout the file. Cell contents are literal text; formula-like values are not executed.
- **PNG and PDF pages flagged for visual review:** the current visual path sends a PNG or one individual native PDF page per analysis request. PDF selection includes empty, failed and detected mixed-visual pages. Searchable model transcription is tagged `origin: ai_visual_transcription` and `verified: false`; it does not become independently verified OCR or participant evidence. Small or rotated text and complex diagrams can be misread. [OpenAI vision limitations](https://developers.openai.com/api/docs/guides/images-vision#limitations)
- **Legacy XLS:** the current runtime has no `xlrd`. Retain the original and report the dependency gap; ask for a copy saved as XLSX or CSV. Do not report successful indexing or install another parser implicitly.

**Re-indexing a file read by an earlier version.** Each stored record carries the `extraction_version` that produced its index. A record with a higher version was indexed by a newer build that shares the store: it is used as it is and Assets says so. A record with a lower or missing version is held back on every read (`extraction_needs_reindex`, review phase `reindex_required`, no coverage credit; the completion gate adds the blocker `documents_reindex_required`), and reading it never writes. Opening or polling the workspace then starts one local comparison (`DocumentStore.check_extraction`, the record's `reindex_check` is `pending` meanwhile): the original is parsed again in memory, with no provider request. When that yields the very sections that are stored (same IDs, labels, text and locations, stored AI transcriptions kept in place), the record takes the new version, inventory and coverage and keeps its review; whether that review is complete is decided again from the new coverage, and no section is rewritten or read again. When the sections differ or the original cannot be read, the outcome is recorded once (`reindex_check.outcome` `changed` or `failed`), the index and review stay untouched, and Assets shows **Needs re-indexing** with the reason. Nothing is sent to the provider until the person chooses **Re-index and review**; opening or polling the workspace never starts that review. That action parses the retained original again and replaces the text index in one transaction. An AI visual transcription is not parser output and can only be produced by a provider review, so it is carried across: where the new index again holds only a visual placeholder for the same source ID, the stored transcription, its continuation parts, its unit in `visual_transcribed_units`, its content digest and its coverage are kept. Text the newer parser reads natively replaces an earlier transcription of that source. Each kept source is listed in the record's `visual_reread_pending` and is offered to the following review as a visual source once more. The placeholder sentences the parser wrote are saved once per record in `visual_reread_basis`, with the coverage limitations the parser alone stated; a pending source holds only the position of its sentence, so a long scan stays a small record. That request is the one a re-index has always sent: the placeholder sentence and location with the page or image, and file-level inventory and coverage that show that unit as not yet read (the stored record keeps counting the kept transcription as read; only the request's copy differs). The stored transcription is not review input until its new reading arrives, and its continuation parts (`_vN`) are left out of review batches, because the new reading replaces those rows; a retained note that cited a part which a shorter new reading removes is pointed at the source itself. The stored text is replaced only when that review returns a transcription. A failed request leaves it in place and pauses the review; an empty reading leaves it in place, is noted as a reading limit and lets the review go on, and the source stays pending for the next explicit re-read. A review is not reported complete while any source is still pending, and Assets says so on the file when no retry button is shown. A new reading that differs from the stored one changes the source text, so confirmed Company knowledge connections that quote it are sent back for review. Assets states the provider cost and this effect above the button, before the click.

Inventory completeness, extraction coverage and AI review progress are separate measures. An inventory entry establishes that a page or tab exists. Indexed text establishes what the parser recovered. A model-reviewed chunk establishes that a bounded analysis request included that source; none of these alone establishes semantic correctness. Shortened inventory previews are explicitly flagged and do not remove the underlying indexed text.

“Complete local extraction” means visiting every accepted page/tab/row and preserving the supported text content within the stated bounds. It does not mean complete visual interpretation of the original. Detected mixed-content PDF pages can receive a separate visual review. Workbook drawings and charts are identified as extraction limitations. Export a chart as a PNG for visual review.

## Question-driven analysis and background review

The integration contract is:

1. On an accepted upload, acknowledge once and stop live voice, release the microphone and drain final captions. Capture the process name, objective, current question and a bounded recent conversation window with the upload, separately from the file's untrusted contents. Concurrent uploads join the pending intake rather than starting another conversation.
2. After local extraction, make a small Responses request using the current question, full unit inventory and selected source chunks. Assess relevance, retain useful questions and exact source IDs in Assets. This early assessment neither claims full review nor triggers an interview question or baseline update.
3. Continue a bounded, incremental sweep through the document's chunks. Persist a review cursor and reviewed/total counts. Merge findings with their sources; apply revision and session guards so a late response cannot replace newer analysis or affect another interview. Work already indexed remains available if the provider fails.
4. Wait for all accepted upload batches, file mutations, active reviews and voice-caption draining to settle. Review phase `complete` is terminal even when `review_complete=false` reports limited coverage. Any active extraction/review error blocks the new baseline until retried, removed or parked; it is not treated as successful review.
5. Build the working notes and workflow from authorized sources, audit the proposed map against those sources and the process boundary, then commit both together. Retain the last accepted capture if generation or audit fails. Only after acceptance request one follow-up using that baseline, transcript and exact excerpts; apply its question without replacing the accepted notes with a second generated snapshot. The server independently rechecks document readiness.
6. Provide a purpose, retry or save-for-later action in Assets. Parked files retain their analysis and questions for explicit discussion. Parking pauses further background review. A request already sent can finish. **Revisit this file** makes the file available for active review again. **Stop review** ends the requests and keeps the file indexed, searchable and readable by the interview; **Continue review** resumes the sweep at its cursor. The reviewer's verdict and its reason are shown with the file. **Use this file anyway** puts a file that was judged unrelated or unclear to use as the participant's own choice (the selection then labels it `disposition_basis: participant_selected` beside the reviewer's verdict), and **Revisit this file** lets the participant word the purpose again. If no new usable file evidence remains, keep the existing capture without inventing a follow-up. New uploads, purpose changes and interview changes invalidate obsolete work. Resume voice only when the participant selects **Continue talking**.

FTS5 is a local lexical index, not OpenAI hosted File Search, vector search or a relational workbook engine. Different terminology, implicit relationships or values lacking the query's words can be missed. A full inventory helps select likely sections; the background sweep broadens review beyond keyword hits over the supported extracted sources. It does not add the visual content omitted by the extraction path. This reduces dependence on initial retrieval but does not guarantee exhaustive understanding. A paused, failed or incomplete sweep must retain that status and its progress rather than report the document fully reviewed.

The implemented sweep batches at most eight chunks and 24,000 text characters, with at most one visual source per request. Retained analysis is bounded to 40 questions, 200 observations and 200 KiB of metadata per document. Reaching a retention bound sets an explicit limitation and prevents the `review_complete` flag even when the sweep reaches its final chunk; full indexed sources remain searchable. Once the questions, the observations and the twelve retained search queries are all full, nothing of a further reply could be kept, so the sweep sends no more text: it ends as `complete` with `review_complete=false`, and `reviewed_chunks` stays at the sections that were actually sent. Pages or images that still need a visual reading are the exception, because a transcription is stored with the file; those are still sent, one per request. The first assessment records `estimated_requests`, about how many requests the whole sweep takes, and Assets shows the share still to come. A page or image whose reading comes back empty (the reply the review instructions prescribe for unreadable content) is recorded as a reading limit for that page; the sweep goes on, the unit stays uncounted and the file is not reported fully reviewed. **Read again** in Assets (action `reread`) asks once more for exactly those pages or images, one per request, and sends no text section a second time. A request that fails for a passing reason (rate limit, timeout, provider-side error) is tried again after 2 and then 8 seconds before the review pauses; an invalid reply is never sent again by itself. A paused review states the kind of provider problem in a fixed sentence chosen by the client's own error category, never the exception text. **Retry review** after a failed in-depth request continues at the persisted cursor; a failed first assessment, a parked file and a file that must be re-indexed are read again from the start, and the first reply of a new reading replaces the notes of the reading before it. Conversation-context selection is smaller again: at most 60,000 excerpt characters in at most 120 chunks (`MAX_SUPPORT_CHARS`, `MAX_SUPPORT_CHUNKS`), shortened summaries, two retained questions and twelve observations per document. A Live voice session start receives a smaller selection still, described under the voice section below. The files of a request are every active file with a prior citation, every active file the browser reports as not yet read in the interview (which includes the files of a running upload), and up to six further active files chosen by match with the latest turns and then by recency. Cited files do not count against those six, and a request that holds an earlier capture (a confirmation after the final check, for example) replays the selection that capture was built on rather than choosing again: the same excerpts and the same files. The coordinator keeps the file list with the capture, because a file that selection had no room to quote has no excerpt to pin and would otherwise drop out of the replay; only a file the browser asks for by name can still join it. A file follow-up that names files to read is not a replay. It is a new reading: what the notes and the browser cite comes first, and the named files take the first turns for the room that is left. A successful conversation request therefore does not mean every stored source or review note was included in that request: the response's `document_reading` field tells the browser how many active files were left out and how many chunks of each included file were sent, and Assets labels a ready file the interviewer has not received as not yet read. Cited excerpts are admitted before anything else, in the order the request lists them across all files (the notes' private citations first in a notes request, the map's own citations first in a map request), with one reservation: when the selected files do not all fit whole, room is kept for the four sections that best match the current turns (`MAX_QUERY_MATCHES`), which are admitted next, so a file whose citations alone would fill a request can still supply the section the conversation has moved to. A cited excerpt that had to wait for them is tried again afterwards. The notes' private citations never wait (`pinned_first`): they are read back before any room is kept, because a fact record loses its tags and outgoing connections when its excerpt is not in the request; once they alone fill the request no match is read, and `omitted_query_matches` in the selection counts the matches that were found and not read. A frozen replay keeps no such room, since it must reproduce the selection it replays. Saved excerpts of parked or removed files follow, within a third of the room (`MAX_RETAINED_CHARS`) so that a removed version cannot crowd out the file that replaced it; what is left of them is admitted at the end if room remains. The other sections come last: matched sections first, then the start, middle and end of each file, then file order, shared between the files in turn. Only when every selected file fits whole is each read in its own order; whether files fit is judged for the selection, not for each file. A cited excerpt that does not fit is not evidence for that request, but it is not treated as missing either: the selection reports it in `carried_sources` as a real excerpt of a file in the scope (ID, file and length, no text). The HTTP handler keeps that list on the server. It is never sent to a model or to the browser. Validation uses it only to let an already accepted map component, finding or private fact keep such a citation; an item that would newly cite one is refused, and so is an ID the store did not report. A map update that restates an accepted step or topic keeps the carried citations that component already had when it adds a source of its own. Any other edit that only keeps them, every restated connection, and the restatement of a step whose accepted handoff cites one are left out of that update: the accepted version stays and the rest of the update is applied. A carried entry that the store flags `retained_only` is a saved excerpt of a parked or removed file; an edit that keeps one is left out even with a source of its own. Every edit that is left out adds one entry to the map's `open_questions` that names the step, handoff or topic. `document_reading.omitted_prior_sources` gives the browser the count, which Assets shows.

Document findings may support documented memo findings, workflow steps and the next interview question through the separate documentary evidence catalog. They must not be placed into participant turns or eligible participant source-ID sets, and cannot establish participant confirmation or completeness. Model instructions embedded in cells, page text or images remain untrusted reference content. Application instructions and permission decisions stay in application code and the trusted provider instruction layer.

## Voice pause and explicit continuation

Ordinary uploads do not stream intermediate context into a speaking voice session. Intake stops the session, releases its microphone and awaits final captions before committing the baseline. The acknowledgment and completed follow-up may use configured question playback, which does not reopen the microphone. **Continue talking** starts a new session after the intake settles.

`CollectorLiveVoice.start({context, turns, voice, document_scope, notes})` forwards the current scope to the local `/api/live-session` endpoint for authorized document-context lookup once at startup. The application does not append those files again after startup. The controller does not retain a scope across calls or put that authorization token in greeting/context events; another interview must supply its own scope explicitly.

**Live session budgets.** `OpenAIClient.live_session` bounds everything it sends at session start. The composed `session.instructions` (static rules, intake context, document data) may not exceed `LIVE_INSTRUCTION_CHARS`, 32,000 characters. The static rules come first and include the application's document-handling rules (`LIVE_DOCUMENT_POLICY`); the block labelled untrusted contains data only, without the document service's `notice` text. Document data takes the room that the rules and the intake context leave. Retrieved context that fits is sent whole. Larger context becomes a digest: each selected file's identity, review state, summary and stated limitations, then whole observations with their source IDs (at most 3,000 characters) and the highest-ranked whole excerpts, shared across files in turn (at most 12,000 characters). The digest ranks each file's excerpts itself, because a file inside the retrieval cap arrives whole in document order: sources that an existing capture cites come first, then excerpts by the retrieval query terms they contain (a term counts for more the fewer retrieved excerpts contain it), with retrieval order deciding ties. The handler passes its own query and preferred source IDs for this purpose as the server-owned `_document_retrieval` field, which is dropped from client input like `_supporting_documents`. Nothing is clipped mid-text. On a first start the opening instruction follows what the block holds: a digest without any summary, observation or excerpt tells the interviewer that the files' text is not in its starting context, instead of asking it to read them. The digest's `context_coverage` reports `complete_text: false` and a `live voice digest` selection, `live_voice_digest` counts what was retrieved and included, and files that do not fit are counted in `omitted_documents`. The delegated model receives the same bounded block, not a second, larger copy. The response reports `document_context.condensed` so the page can say that voice is using a shorter selection of the files. If the intake context alone leaves no room, the request is refused with a message to shorten the background or continue by typing.

Seeded history has its own limit: at most 128 messages and 7,800 UTF-8 bytes (`LIVE_HISTORY_MESSAGES`, `LIVE_HISTORY_BYTES`), a conservative stand-in for the 8,192-token history allowance. A longer transcript is not refused. `live_history` seeds one application message, which states how many turns are omitted and carries the browser's current notes summary (`notes.summary`, trimmed to its share and flagged when trimmed) and topic status (`notes.open_topics` for topics with nothing captured yet, `notes.partial_topics` for topics that hold some detail, as every earlier answer does after a saved interview is reopened), followed by the most recent whole turns that fit. The most recent turn, with the turn before it when both fit, has priority over the summary, whose share shrinks to make room. Only a most recent turn that cannot fit beside the fixed text at all is seeded as its end after the marker `[earlier part of this turn omitted]`, which the message discloses. The response reports `history: {condensed, included_turns, total_turns, summary_included, latest_turn_clipped}` so the page words its notice and hint from what was actually seeded, and `/api/config` publishes `live.history_limit` so the page can warn before **Continue talking** is selected. The managed team's notes requests are unaffected and still use the full transcript. Neither budget has yet been confirmed against the voice service with a long interview or a large file.

**Retained controller capability, not the ordinary upload path:** `CollectorLiveVoice.appendContext(text, {id, kind})` can add concise context to an existing GPT-Live session. It queues during startup and sends `session.thinking.append` only after `session.started`, with `delegation_id: null`. It does not restart voice, create a transcript turn, alter session instructions, or send `session.commentary.append` to request speech.

The first empty-history voice session has a separate opening flow: trusted startup greeting instructions are followed by one `session.commentary.append` after `session.started`. Resumed history and repeated startup events do not repeat that greeting. This opening request is independent of document delivery; its acknowledgment does not establish that the greeting was spoken or played. [GPT-Live opening guidance](https://developers.openai.com/api/docs/guides/live-conversations#greet-before-the-caller-speaks)

For that retained append capability, the controller correlates `session.thinking.appended` through `client_event_id`; `start_ms`/`end_ms` describe context delivery on the session timeline, not spoken acknowledgment or proof of comprehension. Acknowledgments can remain pending while the timeline pauses. A rejected append is handled separately from a failed voice connection. These distinctions follow the [official GPT-Live context contract](https://developers.openai.com/api/docs/guides/live-conversations#add-context-during-the-conversation).

The retained append capability limits each update to 16 KiB of UTF-8 text; its pending queue is bounded to eight updates, 64 KiB of encoded content and 256 events. Each complete append content envelope is at most 480 UTF-8 bytes, a conservative bound beneath the documented 500-token ceiling. Receipts distinguish queued, sent, acknowledged, rejected and cancelled updates. Stop and session replacement clear pending context; old events cannot acknowledge a new session's update. The last 64 completed IDs are cached; revised findings or explicit retries use a new update ID. A historical microphone-free provider probe acknowledged the startup greeting and queued context update. It does not verify the 0.19.0 intake flow, physical audio or live rejection recovery; see the verification receipt for executed scopes.

## Persistence, privacy and recovery

Originals and the SQLite index live in `work/documents/`, outside source control. On POSIX the directory and file modes are 0700 and 0600 respectively. Windows access follows the current user's folder ACL. A Python mode does not set a Windows ACL. Atomic original writes and database transactions protect local consistency. This is private local storage, not encryption at rest or a multiuser identity system.

Every document read, mutation, search, source lookup and original access is authorized by an interview scope token. The database stores its hash. A saved interview's JSON export retains the token and document metadata so the same local installation can reconnect to the stored originals. Treat that export as private because the token authorizes access to its local document scope. A Markdown review can retain human-readable references, but neither format is a portable bundle of the original binaries. Opening a copied interview on another machine requires re-uploading the originals; a missing local scope must not appear to have restored them.

Removal archives a document reversibly. It excludes the file from active retrieval while preserving the original and index for restoration. Archived originals still count toward the scope's file limit. Archive is not permanent erasure; permanent deletion and a user-managed retention policy are separate, unimplemented operations. The interface says so where the action is taken: the button reads **Remove from interview** ("Kept on this computer"), the file notice states that nothing in the app deletes a file, and **Start over** (and opening another interview) names the files that stay. Until a purge exists, the only way to erase uploaded files is the manual one in the README ("Erasing uploaded files"): close the app and delete `work/documents`, which erases every interview's files.

An upload's record keeps where the file was supplied, not the conversation: `context` holds `process_name`, `objective`, `latest_question` (the question the file was added under) and `turn_id` (the participant's turn before it). `DocumentService.upload` no longer copies recent turns into it; records written before that change still hold up to four.

The session and status replies list archived files by name (`removed`), and Assets offers **Restore** for each. They also carry the scope's count (`limit`: `maximum`, `used`, `removed`), which Assets shows as "7 of 20 file slots used, 3 by removed files." When every slot is used, **Add files** is unavailable and the line says why; no file is sent that the store would refuse. A slot is only freed by permanent deletion, which is not implemented. The `restore` action is the inverse of `remove`: it un-archives the file and returns its intent version to the value before removal, so the interview's source identity is unchanged and no review is started. A review that had not finished resumes with ordinary polling. `revisit` also un-archives, but reviews the file again through the provider.

OpenAI Responses requests set `store: false`. The OpenAI quick sample can include file text, content from hidden sheets, and a PDF page or PNG needing visual review. Deep review can send the full extracted text and each page requiring visual review. An estimate above twelve requests or an unrelated verdict pauses the deep review. Save for later pauses review. Remove stops further review. Continue review resumes an explicitly selected file. Interview requests exclude parked, archived and awaiting-purpose files except for excerpts already cited in earlier work.

On parser or provider failure, retain the original, current indexed sources and explicit failure/progress state. A restart can resume pending local work. The final verification must demonstrate recovery and ensure that archived, superseded or differently scoped documents cannot be applied by a late background response.

## Current bounds and dependencies

| Bound | Current value or policy |
| --- | --- |
| Original size and files per interview | 1 byte–64 MiB per original; 20 originals including archives |
| PDF pages | 500; encrypted PDFs require an unlocked copy |
| Workbook sheets, rows and populated cells | 100 sheets; 1,048,576 rows per sheet; 2,000,000 populated cells per workbook |
| Text index | 64 MiB per document; 50,000 chunks; 6,000 characters per chunk |
| AI sweep batch | Eight chunks; 24,000 text characters; one visual source per request |
| Retained AI notes | 40 questions; 200 observations; 200 KiB metadata per document, with explicit limit indicators |
| Individual spreadsheet cell | 100,000 characters |
| Inventory metadata | 50 KiB; shorten preview samples explicitly, and leave them out (`samples_omitted`) when a file has too many units for any sample; retain unit names/counts. A 500-page PDF fits with room to record a visual reading of every page |
| Archive expansion | 512 MiB total, 128 MiB per member; compressed expansion ratio at most 500 |
| PDF decoded content | 16 MiB per page, 128 MiB total |
| PNG | 40 million pixels, plus original-file and provider limits |

`requirements-documents.txt` specifies pypdf 6.10.0, openpyxl 3.1.5 and Pillow 13.0.0 and et_xmlfile 2.0.0. SQLite/FTS5, CSV and ZIP support come from Python's standard library. Legacy XLS conversion is required when the optional xlrd reader is unavailable.

## Deferred capabilities and verification

Managed File Search could add semantic retrieval over a larger corpus; it would introduce hosted file/vector-store lifecycle, deletion, cost and authorization work. Hosted Shell could support deterministic workbook calculations and joins; it would need a bounded analytics workflow and separate artifact/retention controls. Neither capability is implemented by this design. A future Claude adapter could share normalized source locations and analysis schemas, but no Claude provider integration or parity verification is implemented.

The final verification receipt must separately record:

- Complete-corpus fixtures, including a 100-page PDF and a 50-tab workbook with data beyond row 1,000; coordinate/source readback; mixed-content PDF, visual and formula limitations; no silent truncation.
- Scope isolation, malicious file/container handling, permissions, archive/restore, restart recovery and saved-interview references.
- Relevant, ambiguous and unrelated documents; purpose asked once; parked context; progressive findings; provider failure; stale background responses; unchanged participant-evidence and readiness gates.
- Browser upload and source review during an ongoing interview, responsive layouts, export/reopen, one acknowledgment, microphone release/final-caption draining, audited baseline ordering and explicit voice continuation.
- Synthetic provider calls and real microphone/speaker checks, with executed, passed, failed, skipped and unverified scopes stated separately.

Executed results and remaining coverage are recorded in [build verification](BUILD_VERIFICATION.md). Architecture descriptions alone are not verification claims.
