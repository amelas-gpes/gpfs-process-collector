# Interviews with existing documents

Drop one or more supported files onto the interview workspace, or use **Assets → Add files**. The Assets tab is the central place to track uploads, manage files, and read their details and sources. On smaller screens, open **Workspace → Assets**. Both upload methods share the same file limits, progress display and error recovery. Text dragging remains normal; dropping a file outside the upload workspace does not navigate away from an interview.

An accepted upload receives one acknowledgment: the interviewer asks for a moment to digest it. Live voice stops, releases the microphone and waits for final captions. The progress panel shows upload, review and follow-up; initial extraction and quick-review findings do not start competing questions or replace the working diagram.

Once the active files can be asked about, the interviewer asks the one question the files themselves raise: a real gap, contradiction or currentness issue, grounded in an exact excerpt and named so the participant can tell what was read. That question is asked at once, from the files' own excerpts and the conversation so far; it does not wait for the notes or the map. The documented name, sequence, roles, branches and controls then become the next baseline in the background: the notes and the audited workflow of the same revision arrive while the participant answers, with their own status in Notes and Workflow, and are dropped when a newer answer or a file change has overtaken them. The question takes every supplied excerpt into account, so a fuller excerpt answers what a short one leaves open, and it never asks the participant to retell the file. When the model's reply is missing or cannot be asked, the file review's own question is asked instead, provided every source it cites is among the supplied excerpts; the participant is never shown a failure of the model's output. A source may itself identify unresolved assignments; these remain open. Where the concurrent interviewer is not available, the baseline is still built and committed before the question, as before.

A file can be asked about after its first review pass when its text is all indexed and no page or image is waiting for a visual reading (`analysis.question_ready`, set by the server). Its in-depth pass then goes on in the background and the question is not asked a second time as that pass reports progress. Before this, the question waited for the whole review: twelve requests in a row for an 85-page PDF, 161 seconds. A file with a scanned page or an image waits for those readings, because a reading that arrives later changes what an issued question is bound to; once every page and image has been read, the question is released while the rest of the in-depth pass goes on (the inventory's `requires_vision` says that a file has such content and no longer holds the question once it is read: an image read in its first request is asked about at once, and the pages of a scan are read together, 12 pages in about 10 seconds instead of 167). A file the reviewer could not place, or one saved for later, is not asked about. The interview cannot be completed while a review is still running. Up to four files are reviewed side by side. The in-depth batches of one file are sent together, up to 16 at a time (`MAX_DEEP_WAVE`), each answered from the review as it stood when the wave began, and recorded in file order as if they had been asked for one by one; an 84-page PDF's in-depth review takes about 15 to 30 seconds instead of three minutes. Every review request is on the fast tier (`COLLECTOR_FAST_TIER`).

The first notes from a file added before anything is noted or said read the whole file, not the first 60,000 characters (`file_parts.py`). The file is split into consecutive parts of about 7,000 characters, each read by its own request at the same moment with a share of one account's fact budget; two more requests write the account-wide fields (topic states, summary and focus; tags, connections and modules) from the opening of each file, and a topic sweep reads the whole file for the one most telling statement per topic, which is used only for a topic the account covers and no part recorded. A part names the passage behind a fact by line numbers, and the passage is cut from the section's own text, so every quotation is exact. The joined reply goes through the same ledger checks as the single request it replaces, and when a part fails twice the single request is sent instead. Notes added later in an interview, and a file too large (more than 400,000 characters) or too small to split, are captured by the single request as before. Measured: an 84-page PDF's notes after 12 to 15 seconds instead of 55, with all 84 pages read instead of 48.

The post-upload question receives a separate source-first audit using the configured `WORKFLOW_AUDIT_MODEL` (default `gpt-5.4`). A gap in an AI-generated summary cannot override an answer in the original source. For example, a documented next step and owner can be known while the way they receive a handoff remains unclear. Ordinary interview questions retain their normal model.

Select **Continue talking** when ready to resume. The new voice session receives the current file scope at startup for server-authorized source retrieval; files are not appended again as incremental voice updates. The microphone stays off until the participant resumes voice. When the conversation is longer than a new voice session can reload (128 turns or 7,800 bytes of text), voice resumes with a condensed history: the notes summary, the open and partly covered topics and the most recent turns, the latest answer first. The app shows this beside the button beforehand, confirms it once voice is on and keeps it beside the voice controls while that session is on; notes and the report still use the full transcript.

Documentary evidence is distinct from participant confirmation. Notes display **Documented**, with source excerpts available from each citation. The document alone does not establish current practice, exhaustive completeness or owner approval. Current operating steps remain separate from proposed improvements and separate regional processes. Saved interviews retain the cited excerpts; procedure exports include their provenance. Transcript exports list documentary references without embedding the files or their text.

Before a document-based map is accepted, a separate audit checks its proposed edits against the same source excerpts and the process boundary. It checks regional applicability, required signoffs, exception routes, unsupported connections and proposed changes. The source audit uses `gpt-5.4` by default, configurable with `WORKFLOW_AUDIT_MODEL`; the normal interview retains its separately configured model. This additional review takes longer than transcript-only capture; the app shows its progress and retains the last accepted notes and diagram if generation or audit fails. A follow-up failure leaves the newly accepted baseline intact.

Exact sources are retrieved from the current interview's private file scope. Browser-supplied citations cannot authorize new facts. Requests retain prior cited excerpts within a bounded context of up to 60,000 source characters and 120 chunks. Cited excerpts are placed first: the excerpts the notes are built on in a notes update, the map's own citations in a map update. When the notes and the workflow together cite more than one request can read, the remaining cited excerpts are not read again in that request. What already cites them is kept and stays valid, because the file store confirms each one as an excerpt of a file in this interview. Nothing can newly cite an excerpt that was not read. An update to a step or topic that already cites one is applied when it brings a source of its own, such as the latest answer; otherwise that one edit is left out and the rest of the update is applied. An edit that keeps an unread saved excerpt of a parked or removed file is always left out, because such an excerpt can keep what already cites it and cannot support a change. The workflow's open questions name each edit that was left out. Assets states how many cited excerpts the latest update did not read again. Each request carries every active file that is already cited, every active file the interviewer has not yet received readable text from, and up to six further active files: files matching the latest answers first, then the newest. Cited files therefore do not use up the six places, and a newly reviewed file is selected for the baseline update and the follow-up that its own upload starts, where it takes the first turn for the room the cited excerpts leave. One limit remains: when the cited excerpts alone leave less room than one section of the new file, the file receives no text; its upload then says so and Assets labels it as not yet read. A file that was read earlier can be left out of a request, either because it is not cited and not among the six, or because the limit was used up before its turn; when that happens Assets states how many files the latest update left out and marks each of them **Left out of the latest update**. A ready file that has not yet reached the interviewer is labelled **Not yet read in this interview** in Assets, and an upload whose file could not be included says so instead of preparing a follow-up. All of this stays within the same character and chunk limits, so with many cited excerpts a file can still receive only part of its text. Within a file that cannot be given whole, the passages that match the conversation come first: the search runs on the last three turns with the latest answer leading (at most forty distinct words; when there are more, English function words give up their places first), then the passages cited by review notes whose wording matches those turns, then the passages beside each match, the file's first, middle and last passage, and only then the file from its beginning. A file that fits whole is given whole and in its own order. Large or partially readable files disclose omissions and reading limitations. Review phase `complete` means processing has finished; `review_complete=false` can still disclose limited coverage. Voice startup keeps its whole instructions within 32,000 characters: file context that fits is sent whole, and larger context becomes a digest with a smaller selection of whole, exact excerpts (sources the notes already cite, then the excerpts that best match the latest turns) that discloses that selection to the interviewer and to the participant: a notice when voice starts and a line beside the voice controls for the rest of that session. Original files and private scopes remain local and outside Git.

An active file with an extraction or review error blocks the question and the new baseline. Use Assets to retry, remove it or save it for later. On error, **Continue without waiting** resumes with the current capture. Empty or entirely parked uploads leave existing notes and workflow unchanged and do not manufacture a question from older files.

If the file review finishes but the follow-up does not load, use **Try again** in the review panel. A notes or workflow update that fails afterwards is reported in Notes or Workflow with its own retry and does not take the question away. The uploaded file and completed review are retained; re-uploading is unnecessary. A map the page waits for (the legacy baseline path and **Update workflow**) has 120 seconds to be drawn and 240 seconds for its independent source audit with files, 180 without; the browser allows eight and a half minutes for the map and five and a half minutes for a follow-up. A map drawn in the background has 180 seconds to be drawn and 240 for its audit, and the audit's output allowance is 24,000 tokens: reasoning is counted against it, and the earlier 12,000 cut the audit of a longer account off before it could answer. Choose **Continue without waiting** to resume conversation while file review continues. A timeout is reported separately from connection, DNS, or secure-connection failures. Status polling does not retry a failed update or follow-up; explicit retry or a change to the active files can resume it. Local operational diagnostics identify the stage and duration without storing document text, interview content, credentials, or raw provider error messages.

Changing a file's purpose, parking/removing it, or opening another interview invalidates late responses based on its prior state. Prior cited facts survive file removal as saved evidence; removed or parked material cannot silently authorize new workflow claims. Explicit step/route deletions still require a participant correction.

Knowledge submissions resolve documentary citations again on the server and preserve their source type and exact text for review. They do not convert file text into participant testimony or approval.

Assets lists removed files under **Removed files**. **Restore** puts a file back as it was: the interview sees the same source as before the removal and nothing is reviewed again, although a review that had not finished continues. **Revisit this file** is the action that reviews a file again. A citation to a removed or saved-for-later file is submitted as a saved excerpt, flagged for the reviewer; company knowledge does not read that file again. The Submit dialog names such files before you submit and can leave their passages out. A new process cannot rest on such an excerpt alone, and a revision can only where an earlier revision of the same process already holds the passage: Submit process then names the file and the steps or notes involved, and offers **Submit without these citations**. See the [knowledge graph notes](KNOWLEDGE_GRAPH.md).

When you open a saved interview on another computer, its original files may be unavailable there. Until you do something about it, the interview cannot update its notes or working map, and **Submit process** is refused with a message that names the unavailable workspace. In Assets, select **Start new file workspace** to attach local copies. The interview keeps the previous file list and the excerpts it had saved from those files, but only as references: each citation of one is marked "saved reference, file not on this computer". That computer cannot read or check those files and the app never accepts excerpt text from the browser, so these references are not sent with later interview or working-map updates and are left out of **Submit process** (the dialog names the files first). A step or note that also rests on an answer continues on that answer. A step or note that rests on such references alone is not carried into the next update of the working map or notes, and is filed without a source if you submit before then; the notice shown when the new workspace starts says how many there are. Uploading the same original into the new workspace adds it as a new file: it is read again, and earlier citations are not re-attached to it. Save a new interview copy to retain both workspaces' references.

See [build verification](BUILD_VERIFICATION.md) for executed checks and remaining limits; the behavior described here is not a claim of physical microphone or speaker verification.
