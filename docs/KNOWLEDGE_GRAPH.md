# Company knowledge graph: local prototype

## Storage and trust boundary

The graph uses SQLite tables for submission revisions, source entities and typed relationships, proposed cross-process relationships, review history, canonical groups/aliases and background jobs. IDs are globally unique; original submitted records and earlier versions remain available. Reported intra-process relationships are distinct from administrator-confirmed cross-process connections. No name, system, department or similarity alone confirms a dependency. There is no automatically shared or hosted database.

SQLite fits the existing local Python/SQLite prototype without introducing an unsupported graph service. The Azure handoff calls for a managed application, SQL/Blob persistence, Entra-backed authorization and a worker seam; those are future integrations, not resources configured here. A hosted implementation must provide isolation, identity, retention, migration, concurrency, operational recovery and access controls before exposing company data. The current loopback server is not a production multi-user service.

## Local owner development mode

Admin is denied by default. To expose Settings → Admin on a trusted local development machine, explicitly set both `COLLECTOR_DEPLOYMENT_MODE=local` and `KNOWLEDGE_LOCAL_OWNER=true` in the server environment or the ignored repository `.env.local`, then restart the server. This is a local-owner development capability, not an authenticated employee identity or production role system. Anyone with access to the local app under that mode can act as its owner. Do not enable it in hosted/shared use. The reusable authorization seam accepts a server-injected trusted identity provider for `knowledge.admin` and `knowledge.submit`; browser role claims do not grant privileges. Hosted identity, trusted authorizer integration and production authorization remain unimplemented.

Opening the built-in or saved fictional example in local-owner mode adds its bundled process to a separate example graph. Admin switches to an explicitly labeled example view while that interview is active. This sandbox is kept apart from real submissions, cross-process matching and provider analysis; opening the example never spends AI credits. Leaving the example returns Admin to company knowledge. The example graph is available only in local-owner development mode.

Use **Submit process** from More or Review. Submitting files the current interview in company knowledge on this computer and leaves the browser interview available. The filed revision is for administrators; it cannot be loaded back into the interview. To reopen or continue the interview, and to keep the submission's status access, use **Save copy**: the dialog says so before and after submitting and offers **Save copy** once the process is submitted.

An entered participant name is self-reported and distinct from a verified submitter; unknown identity remains unknown. A revision keeps the participant, team, department and scope of the revision before it: the form shows what was last filed (these four fields are saved with the interview file as `knowledge_attribution`), a field the request does not send keeps the earlier value on the server, and a field sent empty is cleared. Every interview carries its own `interview_id`, created with the interview and kept in every saved copy. When a submission without a process ID arrives for an interview the store already holds (a second tab, or a copy saved before the first Submit), nothing is stored and the reply is `409` with `code: "interview_already_submitted"`, the `process_id` and the `revision`; the dialog asks whether to submit a revision or, on purpose, a separate process (`separate_process: true`). Copies of one interview that were filed as separate processes are not offered to the matcher as each other's counterparts. A submission sends only the IDs of its attached files and may be up to 1,000,000 bytes, the store's own limit (`knowledge_submit_max_bytes` in `/api/config`); a larger one is refused by the page before it is sent, and by the server with `413` and `code: "submission_too_large"`. A refused submission carries `not_saved: true` when no record exists under its `submission_key`, which lets the dialog release an attempt it could not confirm earlier; an unconfirmed attempt can also be discarded from the dialog. The local store lives under ignored `work/knowledge/`. It is durable on that machine, not a shared company service, backup or encrypted datastore. Protect it and the separate `work/documents/` workspace according to local data policy. Retained document scope capabilities are kept separately from admin snapshots and provider inputs; authorized admins can retrieve cited local document sources.

The stored graph (steps, roles, systems and handoffs) is built from the review draft when one exists, so corrections made in Review are what the graph holds. The working map is used when no draft has been created, or when a draft that was never edited predates newer answers and the working map has steps (a draft with steps is never replaced by an empty working map). The Submit dialog says which applies and why the draft is flagged (newer answers, a change of the files in use, or only the mark a saved file carried), the `process` and `process_version` entities record `source`, `draft_stale` and `draft_edited`, and Admin's submission detail notes when the graph came from the working map rather than the draft it displays. A draft counts as out of date only when a participant answer, a participant caption or the set of active files changed after it was created. Editing the process title, interviewer messages and file notices do not make it out of date. A saved interview reopens with the state it was saved in. When Review reports an out-of-date draft that already reflects the interview (for example a file re-saved by an earlier build, which flagged every reopened draft), choose **Mark as current** beside the notice; **Update draft** instead rebuilds the draft and replaces edits made in Review.

A submission is a snapshot of the page. The transcript is complete as soon as an answer is sent, but notes and the working map follow by a provider round trip. While that work is running (an answer being processed, notes or the working map updating, voice on, a recording, files being read, a completion review), **Submit process** waits and says what it is waiting for. When the work has stopped short, for example because the provider was unavailable, the dialog names what the revision would lack and offers **Submit anyway**. Every submission stores a `capture` marker: `in_progress`, `notes_current`, `map_current`, `notes_through_turn` and `map_through_turn` from the browser, plus the answer counts the server derives after checking the marker against the transcript. Admin flags a revision filed that way in the submissions list and explains it in the detail. The server cannot observe a capture that was still running, so a revision without a marker (an older client or file) is shown as "Not recorded". An interview reopened from a file without a marker has only an assumed position: once an answer is added, the dialog says that notes and the working map do not include the latest answer, the marker carries `notes_assumed` / `map_assumed`, and Admin reports the latest answers as missing and the earlier coverage as not recorded instead of a count. Voice and a recording do not end by themselves, so for those the dialog says what to do (stop talking, or finish the recording) instead of waiting. While **Create draft** or **Update draft** runs, Submit waits so that the draft is included; a draft that arrives after a submission was already on its way is named on the receipt. **Save copy** keeps the same marker, and a reopened interview still knows where its notes and working map stopped.

The interview keeps a citation to a file that was removed or saved for later as a saved excerpt, and so does a submission. The server reads the cited passage in the interview's own file scope and stores it in `document_evidence` flagged `retained_only` (with `archived` and `disposition`); the file is listed under `documents.retained`, apart from the active files in `documents.documents`. Company knowledge uses a file only while its interview does. A file that is removed or saved for later when the process is submitted gets no entry among the active files, so Admin cannot open it through that revision; a file saved for later that nothing cites is left out altogether. Whenever a file is removed or saved for later, including after a submission that listed it, its text is no longer placed in a matching request and it cannot back a proposal as document-supported evidence; a proposal that already quotes it goes back for review. The same holds for a page or image that has not been read: its placeholder sentence ("requires native visual review") is not file content, so it is never a matching excerpt or document-supported evidence, while an AI visual transcription stays eligible and marked unverified. Each cited step, connection or note is judged on its own. A saved excerpt may stay beside other evidence (a participant answer, the supplied context or a file in use). A part may rest on saved excerpts alone only in a revision, and only on passages that an earlier revision of the same process already holds; a new process cannot rest on a saved excerpt alone, a revision cannot bring a removed or saved-for-later file's passage in that way either (so the Submit that follows **Submit without these citations** does not file what was left out), and a citation whose passage cannot be read at all is not stored. Before submitting, the dialog names the files that are no longer in use but still cited, says that their cited passages are stored as saved excerpts where administrators can read them, and offers to leave those passages out of the submission. That holds only for a file the current file workspace still has (listed, or among its removed files). A cited file that is not among the interview's files on this computer (the interview was reopened elsewhere, or a new file workspace was started) cannot be read, so the dialog says that its passages cannot be stored and have to be left out, and such a workspace is not sent as the submission's files. When Submit process is refused for this reason, the dialog names the file and the steps or notes that cite it and says what to do: **Restore** a removed file or **Revisit this file** for a saved-for-later one in Assets, or **Submit without these citations**, which files a copy of the snapshot without the named citations and leaves the interview unchanged.

Where revisions are permitted (local-owner mode, or a verified owner or administrator), a revision must come from a copy that is based on the latest one. The dialog sends the revision its copy was filed as (`base_revision`). When a newer revision exists, for example because an older saved copy or a stale tab was opened, the dialog says "This copy is based on revision 1; the latest is revision 2" as soon as it opens, and the server refuses the revision (409, nothing stored) until the submitter ticks **Submit this copy as revision N anyway**, which names the latest revision they were shown. Earlier revisions are always kept.

The submitter can refresh the status of the submitted revision using a private, narrowly scoped status capability. The capability cannot open the administrative graph. Saving the interview JSON retains it for reopening, so treat that JSON as private; it is not sent to the AI analyzer or included in administrative records.

## Keeping and removing submissions

A submitted process stays in `work/knowledge/knowledge.sqlite3` with every revision: the self-reported participant name, the full transcript, the draft, and a copy of each cited file passage. **Start over** and closing the interview do not remove it, and a later revision adds a row and keeps the earlier ones. The Submit dialog says so before sending. Deleting is off by default.

To let an administrator delete a submitted process, set `KNOWLEDGE_ADMIN_DELETE=true` beside the two local-owner settings and restart. Admin's submission detail then offers **Delete this process**: a reason, the typed word DELETE, and the latest revision shown (a revision filed meanwhile is not removed unseen). One transaction removes the process's revisions, graph entities and relationships, processing jobs, status capabilities, document scope and submission keys, every suggested or reviewed connection that quotes it together with that connection's review history, and its memberships of reviewed groups (those groups are marked for review). The store keeps a record without content in `deletions`: the identifiers, the number of revisions and connections removed, who deleted it, the reason and the time. The database runs with `secure_delete` and the write-ahead log is folded in afterwards, so the removed text is overwritten in the SQLite files; backups, saved interview files and the files uploaded under `work/documents/` are not touched. The holder of a deleted revision's status capability is told that the process was deleted. Text already sent to the AI provider for matching cannot be recalled.

Without the switch, removing one submission is a manual step for the owner of the computer, with the app stopped, against a backup-safe copy of the file. In this order (the `sqlite3` module of the app's Python is enough; `:sid` is the `submission_id` shown under Technical record):

```sql
PRAGMA foreign_keys=ON; PRAGMA secure_delete=ON; BEGIN IMMEDIATE;
DELETE FROM review_history WHERE proposal_id IN (SELECT id FROM proposals WHERE json_extract(data,'$.source_submission_id')=:sid OR json_extract(data,'$.destination_submission_id')=:sid);
DELETE FROM proposals WHERE json_extract(data,'$.source_submission_id')=:sid OR json_extract(data,'$.destination_submission_id')=:sid;
DELETE FROM canonical_members WHERE entity_id IN (SELECT id FROM entities WHERE submission_id=:sid);
DELETE FROM edges WHERE submission_id=:sid; DELETE FROM entities WHERE submission_id=:sid;
DELETE FROM jobs WHERE submission_id=:sid; DELETE FROM status_capabilities WHERE submission_id=:sid; DELETE FROM private_documents WHERE submission_id=:sid;
DELETE FROM submission_keys WHERE json_extract(receipt,'$.submission_id')=:sid;
DELETE FROM revisions WHERE submission_id=:sid;
COMMIT; PRAGMA wal_checkpoint(TRUNCATE);
```

Removing everything is simpler: stop the app and delete the `work/knowledge/` folder; an empty store is created at the next start.

Document-derived simulated interviews can be retained as real process records without claiming an
employee supplied the account. Their optional `capture_provenance` has `method:"document_simulation"`,
1–20 source documents identified by filename and SHA-256, and both `participant_confirmed:false` and
`process_owner_approved:false`. Such submissions cannot set interview closure confirmation to true.
Admin labels the simulation and its source filenames. Transcript quotations from these records use
`simulated_document_account`, including when a model proposes an employee-evidence label incorrectly.
The source declaration does not verify actual practice or control execution. Connections remain
proposals pending authorized review, and the ordinary employee-interview flow keeps its existing labels.

With a configured compatible text provider, a background worker compares a bounded sample of participant statements and creates review proposals. Text from employee submissions is untrusted input and is never an instruction. Quotes are checked against participant statements or authorized exact document locations on both source revisions, and model output cannot confirm a connection. The current analyzer compares a process with the eight most recent other processes whose latest revision has a compatible scope (the same scope without regard to case, or no scope), however many submissions of other scopes are newer; the job records how many compatible processes were left out and the request tells the model. It uses bounded participant excerpts, and at most two document-source excerpts per submission, so completed processing is not exhaustive company coverage. Document-supported and employee-reported evidence remain distinct; visual transcriptions are not verified facts. When no provider is configured, the submission remains saved and its job waits. A waiting job (filed without a provider, queued when the app stopped, or interrupted) runs by itself the next time the app starts with a provider configured, oldest first; this is the one matching call that Submit announced. A job that has already been started three times is left for an administrator to retry, so a job that stops the app cannot do so at every start. The submitter's **Refresh status** says when analysis has not started and starts the caller's own waiting job when a provider is available; the Admin overview counts jobs that have waited more than five minutes (`processing_stalled`). Provider calls can incur usage charges; no OpenAI key is sent to the browser.

Administrators can inspect source submissions and review proposals, record side-specific statements independently, filter records, view reported and confirmed links, and maintain explicitly reviewed canonical groups and aliases. Removing a mistaken group member retains the original source entity and an audit trail. No automatic merging is performed across processes. Within one revision, a role, system, team, scope or business object that several steps name is stored once, with one relationship per step that names it, so a reviewed group needs one selection per process and Admin shows each entity with its process and the steps that name it. When a revision makes a group stale, **Replace outdated members with the latest revision's entities** exchanges each outdated member for the entity of the same type and label in the latest revision; the administrator then reviews and revalidates. The Graph view can be narrowed by label text and, at All entities, by entity type. Source revisions mark dependent proposals stale rather than silently carrying forward approval. Each suggested connection in a matching response is checked on its own: one that fails a check (a quote that is not verbatim, evidence from one side only, a wrong revision or scope) is dropped and never stored, the others are kept and the job completes. The Processing list shows for each job how many processes it compared, how many suggestions were dropped and the check each failed. A job that fails says what stopped it: the AI provider (with the provider message this app worded), a result that could not be used, or an error in this app, so Retry, which is a new paid request, is not pressed blindly; the kind and the exception class also go to `work/server-lifecycle.jsonl` (`knowledge_job_failed`), without content. Failed or interrupted processing remains visible for retry; repeated jobs do not intentionally create duplicate reviewed claims.

Administrative lists load metadata in pages of 25 (API maximum 50). Full submission details, exact evidence, group members, aliases and review histories load separately; every retained record remains available. Filters run over the full stored dataset on the server. Offset pages may shift when records change; Refresh restarts them. Lists and related-route histories show the last recorded connection status. Opening a connection, rendering a bounded graph or reviewing a decision rechecks the selected document evidence. A complete graph exceeding 80 nodes or 150 connections requires a narrower selection; the app never silently truncates its topology. See the [Admin API contract](ADMIN_API_CONTRACT.md).

Older browser Admin clients receive an update message instead of an unbounded snapshot. The launcher also detects when an older backend is still running, so users can save and restart it or open the new build on another port without interrupting an existing interview.

The graph is reported knowledge rather than an execution-event system. Its graph traversal uses recorded relationships, not operational measurements or proven consequences. Missing routes, evidence and employee disagreement are not proof of a control failure. No event ingestion, measured throughput, hosted identity, shared cloud graph, natural-language graph answering or production admin security is implemented. Source documents and submission records may contain sensitive information; export and share them only under the organization's policies.
