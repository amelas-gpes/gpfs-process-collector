# Filed processes and revisions

## Filing and revision access

Use **Submit process** from More or Review to file an immutable revision on this computer. It includes the transcript, participant attribution, draft, map and cited evidence. **Save copy** downloads the editable interview and carries the receipt needed to check that revision’s status. Closing the interview or starting over leaves filed revisions in the local store.

The server checks permission before filing a revision. A trusted identity with `knowledge.submit` can revise its own submission. An identity with the existing `knowledge.admin` capability can revise any submission. For a trusted single-user loopback installation, both `COLLECTOR_DEPLOYMENT_MODE=local` and `KNOWLEDGE_LOCAL_OWNER=true` grant local-owner revision authority. Browser-supplied role claims do not grant access.

An entered participant name is self-reported and distinct from a verified submitter; unknown identity remains unknown. A revision keeps the participant, team, department and scope of the revision before it: the form shows what was last filed (these four fields are saved with the interview file as `knowledge_attribution`), a field the request does not send keeps the earlier value on the server, and a field sent empty is cleared. Every interview carries its own `interview_id`, created with the interview and kept in every saved copy. When a submission without a process ID arrives for an interview the store already holds (a second tab, or a copy saved before the first Submit), nothing is stored and the reply is `409` with `code: "interview_already_submitted"`, the `process_id` and the `revision`; the dialog asks whether to submit a revision or, on purpose, a separate process (`separate_process: true`). Copies of one interview that were filed as separate processes are not offered to the matcher as each other's counterparts. A submission sends only the IDs of its attached files and may be up to 1,000,000 bytes, the store's own limit (`knowledge_submit_max_bytes` in `/api/config`); a larger one is refused by the page before it is sent, and by the server with `413` and `code: "submission_too_large"`. A refused submission carries `not_saved: true` when no record exists under its `submission_key`, which lets the dialog release an attempt it could not confirm earlier; an unconfirmed attempt can also be discarded from the dialog. The local store lives under ignored `work/knowledge/`. It is durable on that machine, not a shared company service, backup or encrypted datastore. Protect it and the separate `work/documents/` workspace according to local data policy. The store keeps document scope capabilities separately from provider inputs.

The stored graph (steps, roles, systems and handoffs) is built from the review draft when one exists, so corrections made in Review are what the graph holds. The working map is used when no draft has been created, or when a draft that was never edited predates newer answers and the working map has steps (a draft with steps is never replaced by an empty working map). The Submit dialog says which applies and why the draft is flagged (newer answers, a change of the files in use, or only the mark a saved file carried). The `process` and `process_version` entities record `source`, `draft_stale` and `draft_edited`. A draft counts as out of date only when a participant answer, a participant caption or the set of active files changed after it was created. Editing the process title, interviewer messages and file notices do not make it out of date. A saved interview reopens with the state it was saved in. When Review reports an out-of-date draft that already reflects the interview (for example a file re-saved by an earlier build, which flagged every reopened draft), choose **Mark as current** beside the notice; **Update draft** instead rebuilds the draft and replaces edits made in Review.

A submission is a snapshot of the page. The transcript is complete as soon as an answer is sent, but notes and the working map follow by a provider round trip. While that work is running (an answer being processed, notes or the working map updating, voice on, a recording, files being read, a completion review), **Submit process** waits and says what it is waiting for. When the work has stopped short, for example because the provider was unavailable, the dialog names what the revision would lack and offers **Submit anyway**. Every submission stores a `capture` marker: `in_progress`, `notes_current`, `map_current`, `notes_through_turn` and `map_through_turn` from the browser, plus the answer counts the server derives after checking the marker against the transcript. Older clients and saved files can lack a capture marker. An interview reopened from a file without a marker has only an assumed position: once an answer is added, the dialog says that notes and the working map do not include the latest answer. The marker carries `notes_assumed` / `map_assumed`. Voice and a recording do not end by themselves, so for those the dialog says what to do (stop talking, or finish the recording) instead of waiting. While **Create draft** or **Update draft** runs, Submit waits so that the draft is included; a draft that arrives after a submission was already on its way is named on the receipt. **Save copy** keeps the same marker, and a reopened interview still knows where its notes and working map stopped.

The interview keeps a citation to a file that was removed or saved for later as a saved excerpt, and so does a submission. The server reads the cited passage in the interview's own file scope and stores it in `document_evidence` flagged `retained_only` (with `archived` and `disposition`); the file is listed under `documents.retained`, apart from the active files in `documents.documents`. Company knowledge uses a file only while its interview does. A file that is removed or saved for later when the process is submitted gets no entry among the active files; a file saved for later that nothing cites is left out altogether. Whenever a file is removed or saved for later, including after a submission that listed it, its text is no longer placed in a matching request and it cannot back a proposal as document-supported evidence. The same holds for a page or image that has not been read: its placeholder sentence ("requires native visual review") is not file content, so it is never a matching excerpt or document-supported evidence, while an AI visual transcription stays eligible and marked unverified. Each cited step, connection or note is judged on its own. A saved excerpt may stay beside other evidence (a participant answer, the supplied context or a file in use). A part may rest on saved excerpts alone only in a revision, and only on passages that an earlier revision of the same process already holds; a new process cannot rest on a saved excerpt alone, a revision cannot bring a removed or saved-for-later file's passage in that way either (so the Submit that follows **Submit without these citations** does not file what was left out), and a citation whose passage cannot be read at all is not stored. Before submitting, the dialog names the files that are no longer in use but still cited, says that their cited passages are stored as saved excerpts, and offers to leave those passages out of the submission. That holds only for a file the current file workspace still has (listed, or among its removed files). A cited file that is not among the interview's files on this computer (the interview was reopened elsewhere, or a new file workspace was started) cannot be read, so the dialog says that its passages cannot be stored and have to be left out, and such a workspace is not sent as the submission's files. When Submit process is refused for this reason, the dialog names the file and the steps or notes that cite it and says what to do: **Restore** a removed file or **Revisit this file** for a saved-for-later one in Assets, or **Submit without these citations**, which files a copy of the snapshot without the named citations and leaves the interview unchanged.

Where revisions are permitted (local-owner mode, or a verified owner or administrator), a revision must come from a copy that is based on the latest one. The dialog sends the revision its copy was filed as (`base_revision`). When a newer revision exists, for example because an older saved copy or a stale tab was opened, the dialog says "This copy is based on revision 1; the latest is revision 2" as soon as it opens, and the server refuses the revision (409, nothing stored) until the submitter ticks **Submit this copy as revision N anyway**, which names the latest revision they were shown. Earlier revisions are always kept.

The submitter can refresh the status of the submitted revision using a private, narrowly scoped status capability. Saving the interview JSON retains it for reopening, so treat that JSON as private; it is not sent to the AI analyzer.

## Matching and historical records

Knowledge store format 3 protects filed revisions, review history, canonical group history and historical deletion receipts. Every application connection enables SQLite triggers that reject updates, deletions and replacements of those rows. This includes rows carried forward from older stores. A correction appends a new revision. Builds supporting only formats 0–2 refuse the upgraded store.

Trusted authorization integrations supply the complete principal identifier for each capability. The app accepts 1–200 printable characters with no leading or trailing whitespace. An invalid identifier grants no capability. The local-owner option conveys revision authority on the local machine and supplies no verified employee identity.

When a compatible text provider is available, the background worker compares the filed revision with up to eight recent eligible processes in compatible scopes. It sends bounded participant excerpts and up to two eligible document excerpts per submission. Each proposed connection must reference both revisions and pass evidence checks before it is stored. Provider calls can incur charges. The participant can check status using their receipt.

A submission filed without a provider stays on disk. On startup with a provider, the worker resumes eligible waiting or interrupted jobs, oldest first, up to its automatic attempt limit. A job that exhausts that limit reports failure on the receipt. Its filed revision stays available. **Refresh status** can also start the receipt holder’s eligible waiting job.

A document-simulated process can carry `capture_provenance` with source filenames and SHA-256 identifiers. These records keep their simulation evidence labels and unconfirmed participant and owner status.

Older databases can contain earlier review decisions, canonical groups and deletion receipts. Those records stay in place when the app opens the store. For local retention and developer trace locations, see [data handling](DATA_HANDLING.md).
